# PRD: 비용 최적화와 답변 표현 개선

작성일: 2026-10-15 · 상태: 초안 · 상위 PRD: `PRD-kbap-pm-agent.md`

## 1. 요약

첫 실제 질문 한 건이 기록상 1.60달러, 첫 진행 표시까지 11초였다. 200달러 예산으로 125질문밖에 못 한다는 뜻이다. 비용을 질문당 0.3달러 아래로 내리고, 답변의 마크다운과 지표 차트를 화면에서 제대로 보이게 한다. 실제 사용이 막 시작된 지금, 예산이 소진되기 전에 고쳐야 한다.

## 3. 배경

2026-10-15 운영 배포 직후 사용자가 실제 질문 1건을 보냈다. 운영 DB의 호출 기록은 다음과 같다.

| 항목 | 측정값 |
|------|--------|
| 모델 호출 턴 | 6회 (Sonnet 5.5) |
| 첫 턴 입력 토큰 | 124,786 |
| 6턴 입력 토큰 합계 | 780,309 |
| 출력 토큰 합계 | 4,031 |
| 기록된 비용 | $1.60 |
| 도구 결과 전체 크기 | 약 15,000자 (약 5,000토큰) |
| 첫 진행 표시까지 | 11초 (목표 5초) |

도구 결과는 5천 토큰뿐인데 첫 턴부터 12만 토큰이 들어갔다. 원인은 두 가지로 확인됐다.

1. **Amplitude MCP 도구 정의가 매 턴 통째로 들어간다.** 서버가 도구 49개, 약 30만 자(7만 7천 토큰 이상)를 내려주고, 우리는 전부 모델에 넘긴다. 실제 질문에서 쓴 도구는 `get_amplitude_context`와 `query_amplitude_data` 둘뿐이다. 목록에는 `delete_event_properties`, `manage_amp_taxonomy` 같은 쓰기·삭제 도구도 있어 "Amplitude는 조회 전용"이라는 상위 PRD 비목표와도 어긋난다.
2. **캐시 읽기를 정가로 집계한다.** 프롬프트 캐싱은 켜져 있지만, 사용량 기록이 캐시 읽기 토큰을 일반 입력 토큰과 합쳐 정가(10배)로 계산한다. 실제 청구액은 1.60달러보다 낮을 가능성이 크지만, 분리 기록이 없어 얼마인지 모른다.

에이전트 구조(턴 6회)는 세 번째 요인이다. 턴마다 누적 맥락을 다시 보내므로 턴 수와 모델 단가가 곱해진다. 위 두 가지를 고친 뒤에도 남는 비용은 여기서 나온다.

답변 표현 쪽은 별개 문제다. 에이전트 답변 본문은 마크다운인데 화면이 평문으로 보여 주고, 근거의 지표 수치는 숫자 한 줄로만 나와 추세를 볼 수 없다.

## 4. 목표

**목표:** 질문 한 건의 비용과 대기 시간을 PRD 기준 안으로 되돌리고, 답변을 읽고 판단하기 쉬운 형태로 보여 준다.

**핵심 결과 (적용 후 실제 질문 10건 기준, 수치는 가정 — 7.4 참고):**
1. 질문당 실제 청구 비용 평균 0.30달러 이하. 캐시 읽기를 분리 기록한 값으로 측정.
2. 첫 진행 표시까지 5초 이내 (상위 PRD SC-004), 완성 제안까지 3분 이내.
3. 제안·실행 단계 텍스트의 마크다운과 본문의 GFM 표가 화면에서 렌더링되고, 지표 근거에 시계열이 있으면 차트로 보인다. 10건 중 10건.
4. 품질 회귀 게이트: 10건에서 인용 지표의 Amplitude 일치율 90% 이상(상위 PRD SC-003 유지)이고, 변경 전 같은 질문의 답변과 비교해 근거(지표·코드 위치) 누락이 없다. 비용·속도 목표를 달성해도 이 기준에 미달이면 적용하지 않는다.

## 5. 대상 세그먼트

**세그먼트 A — 예산을 관리하는 운영자**
200달러로 몇 질문을 할 수 있는지, 어디서 돈이 나가는지 알아야 한다. 지금은 집계가 틀려 판단 근거가 없다.

**세그먼트 B — 답변을 읽고 결정하는 개발자**
제안을 읽고 채택·보류를 정한다. 표와 목록이 깨져 보이고 추세를 숫자로만 보면 판단이 느리다.

**제약:**
- 사용자 2명, 예산 200달러.
- 계약서의 SSE 이벤트와 제안 4부 구조는 유지한다. 근거 필드는 추가만 허용.
- Amplitude는 조회 전용이다.

## 6. 가치 제안

### 세그먼트 A — 예산을 관리하는 운영자

- **누구:** LLM 예산을 책임지는 개발자
- **왜:** 질문당 비용을 알고 통제해야 한다. 지금은 1.6달러로 보이지만 진짜 값인지도 모른다.
- **이전:** 캐시 토큰이 정가로 합산된 숫자만 있다. 도구 정의 7만 토큰이 매 턴 나가는 줄 몰랐다.
- **방법:** 쓰는 Amplitude 도구만 허용 목록으로 넘기고, 캐시 생성·읽기 토큰을 따로 기록해 실제 단가로 계산한다. 그 뒤 조사 단계는 싼 모델, 종합 단계는 강한 모델로 나눈다.
- **이후:** 질문당 비용이 수십 센트로 내려가고, 호출별 내역에서 어디에 쓰였는지 보인다.
- **대안:** 턴 상한을 더 낮추기(품질 하락), 모델을 Haiku로 통일하기(제안 품질 하락). 우리를 택하는 이유: 품질을 건드리지 않는 두 가지(도구 목록, 집계)가 비용의 대부분을 차지한다.

**가치 제안 문장:** 품질을 깎지 않고 질문당 비용을 5분의 1로 줄이고, 그 숫자를 믿을 수 있게 한다.

### 세그먼트 B — 답변을 읽고 결정하는 개발자

- **누구:** 제안을 읽고 채택을 결정하는 개발자
- **왜:** 근거를 빨리 파악해야 결정이 빠르다. 추세와 비교는 표나 차트가 글보다 빠르다.
- **이전:** 마크다운이 평문으로 보여 표가 깨지고, 지표는 "41.3%" 한 줄이다.
- **방법:** 본문을 마크다운으로 렌더링하고, 지표 근거에 시계열 데이터가 있으면 작은 차트로 그린다.
- **이후:** 제안 카드에서 추세를 보고 바로 채택 여부를 정한다.
- **대안:** Amplitude 콘솔을 열어 차트를 직접 본다. 우리를 택하는 이유: 근거 옆에 바로 보이니 왕복이 없다.

**가치 제안 문장:** 근거를 글이 아니라 표와 차트로 보고 결정한다.

## 7. 솔루션

### 7.2 첫 버전 필수 기능

비용 (효과 큰 순서):
- **Amplitude 도구 허용 목록.** 환경변수로 지정한 도구만 모델에 넘긴다. 기본값은 조회 도구 몇 개(`get_amplitude_context`, `query_amplitude_data`, 차트·택사노미 조회 등 읽기 전용). 쓰기·삭제 도구는 제외. 예상 효과: 턴당 입력 7만 토큰 이상 감소, 첫 응답 지연 대폭 단축.
- **캐시 토큰 분리 기록과 단가 적용.** 사용량 테이블에 캐시 생성·읽기 토큰 컬럼을 추가하고 공급자별로 정규화해 계산한다. Anthropic은 캐시 생성·읽기 토큰이 따로 오고(읽기 10%, 생성 125%), OpenAI는 전체 입력 토큰 안에 캐시 토큰이 포함돼 오며 생성 개념이 없다. 공급자·모델별 단가표와 정규화 규칙을 명시해 이중 계산을 막는다. 화면의 비용 표시도 이 값을 쓴다.
- **조사·종합 2단계와 모델 차등.** 조사 단계(도구 루프)는 싼 모델, 종합 단계(도구 없이 1회, 제안 작성)는 강한 모델. 종합 입력은 도구 결과의 요약과 함께 정확도에 필요한 구조화 근거(지표 시계열·수치, 코드 발췌와 위치)를 손실 없이 넘긴다. 현재 요약은 첫 줄 500자뿐이라 그대로 쓰면 수치·위치가 사라진다. 상위 PRD의 턴 상한·시간 상한은 유지. (철회됐던 설계를 비용 근거가 생긴 지금 다시 포함)
- **호출별 비용 내역.** 사용량 기록에 단계(stage) 필드를 두고, 메시지 응답의 usage는 합계 하나가 아니라 호출별 항목 배열(단계·모델·토큰·비용)로 내린다. 현재는 메시지 단위로 합산하고 모델을 `MIN(model)`로 하나만 표시해 두 모델을 쓰면 임의 값이 된다. 설정 화면 예산 현황에 누적을 보인다. 원화 표시는 1달러 1,300원 환산.

표현:
- **마크다운 렌더링.** 답변 본문은 이미 react-markdown으로 렌더링된다. 빠진 것은 제안·실행 단계 텍스트(현재 평문)와 GFM 표 지원이다. 이 둘만 추가한다.
- **지표 차트.** 근거 `kind: metric`에 선택 필드 `series`(시점·값 배열)를 추가한다. 있으면 카드 안에 작은 선·막대 차트, 없으면 지금처럼 수치만. 에이전트 프롬프트에 "시계열을 받았으면 series로 넘겨라"를 추가.

### 7.3 기술

- 도구 허용 목록은 MCP 도구 목록을 받은 뒤 이름으로 거르는 함수 하나. Anthropic 런타임은 도구 목록에, OpenAI 런타임은 MCP 서버 객체에 각각 같은 함수를 적용한다(공통 후처리 래퍼가 없으므로 한쪽만 걸면 다른 쪽은 전부 받는다).
- 캐시 컬럼은 `llm_usage`에 2개 추가. 기동 시 적용되는 스키마는 `CREATE TABLE IF NOT EXISTS`라 운영 테이블에 컬럼이 생기지 않으므로, 멱등 `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` 마이그레이션을 두고 앱 갱신보다 먼저 실행한다. 기존 행은 캐시를 분리할 수 없어 `추정치` 표시를 붙이거나 예산 기준선을 적용 시점으로 재설정한다. 그대로 두면 첫 질문의 과대 기록이 누적 예산에 계속 남는다.
- 차트는 의존성 작은 라이브러리 하나(수백 KB 이하). 디자인은 하지 않는다.
- 마크다운은 검증된 렌더러 하나. HTML 삽입은 허용하지 않는다(모델 출력이므로).

### 7.4 가정과 열린 질문

**가정 (검증 필요):**
- 핵심 결과 수치(0.30달러, 10건 중 10건)는 작성자 제안이다.
- 도구 허용 목록만으로 첫 턴 입력이 12만에서 1만 토큰대로 내려간다. (도구 정의 크기 측정값 기준 추정)
- 실제 청구액은 캐시 적중으로 기록값보다 낮다. 분리 기록 후 확인.
- 2단계 분리의 추가 절감은 측정 후에만 안다. 도구 허용 목록과 집계 수정을 먼저 적용하고 10건을 재어 본 뒤 2단계를 넣는다.
- Amplitude 조회 도구가 시계열 배열을 돌려준다(`query_amplitude_data` 응답 형식 확인 필요).

**열린 질문:**
- 종합 단계 모델: Opus 5.5인지 Fable 5.1인지. Fable은 단가 2.5배, 요청이 수 분 걸릴 수 있고 30일 데이터 보존 설정이 필요하다.
- 허용 목록에 넣을 Amplitude 도구의 정확한 집합. 허용 목록이 켜진 뒤의 호출 기록은 허용된 도구만 담으므로 근거가 될 수 없다. 확장 판단은 빈 허용 목록(전부 허용)으로 돌린 섀도 질문 몇 건의 호출 패턴으로 한다.
- 차트 종류를 선·막대 두 가지로 제한할지.
- 첫 진행 표시 11초의 나머지 원인. 도구 정의를 줄인 뒤에도 5초를 넘기면 응답 스트리밍 시작 시점을 봐야 한다.

## 8. 릴리스

**1단계 (며칠):** 도구 허용 목록, 캐시 토큰 분리 집계, 호출별 내역 기록, 마크다운 렌더링. 적용 후 실제 질문 10건 측정.
**2단계 (측정 결과 보고):** 조사·종합 2단계와 모델 차등, 지표 차트(`series` 필드 + 프롬프트).
**다음:** 역할별 다중 에이전트(일일 리포트 등)는 2단계 결과가 나온 뒤.

**하지 않는 것:**
- 턴 상한·시간 상한 변경 (상위 PRD 유지)
- Amplitude 쓰기 도구 사용
- 차트 디자인·대화형 차트
- 모델 출력 HTML 렌더링
