# PRD: K-Bap PM Agent

작성일: 2026-10-15 · 상태: 초안 (프로토타입 단계)

## 1. 요약

K-Bap PM Agent는 개발자 2명뿐인 팀에서 기획자 역할을 대신하는 에이전트다. 이벤트 택사노미(정의), FE 코드(맥락), Amplitude(지표)를 함께 읽고 종합해, "다음에 무엇을 만들지", "그것을 어떻게 측정할지"를 근거와 실행안까지 붙여 제안한다. 앱이 배포되어 데이터가 쌓이고 있지만 그것을 보고 결정할 사람이 없는 지금이 적기다.

## 3. 배경

K-Bap은 배포된 서비스로 Amplitude에 이벤트가 수집되고 있다. 팀은 개발자 2명이고 기획 전담자가 없다. 그래서 다음 세 가지가 비어 있다.

- **결정:** 데이터를 보고 다음 기능의 우선순위를 정하는 일
- **설계:** 기능을 측정할 퍼널과 이벤트를 설계하고, 코드 어디에 심을지 정하는 일
- **점검:** 캠페인이나 배포 뒤 지표가 어떻게 바뀌었는지 해석하는 일

이 일은 단순 조회가 아니다. 이벤트가 무엇을 뜻하는지(택사노미), 실제로 어느 화면·어느 동작에서 발생하는지(코드), 실제 수치가 어떤지(Amplitude)를 한 머릿속에 넣고 생각해야 한다. 지금은 그 머리가 없다.

왜 지금인가:
- 데이터는 이미 쌓이고 있다. 해석과 결정만 비어 있다.
- Amplitude가 공식 원격 MCP 서버(https://mcp.amplitude.com/mcp)를 제공한다. 세그멘테이션·퍼널·리텐션 조회와 택사노미 도구를 OAuth로 바로 쓸 수 있다. (출처: https://amplitude.com/docs/mcp)
- 코드 분석용 Claude API 크레딧 200달러가 확보되어 있다.
- Figma MCP, Jira MCP 같은 실행 도구가 갖춰져 있어, 제안을 시안·이슈로 바로 이어갈 길이 열려 있다.

## 4. 목표

**목표:** 개발자 2명이 기획자 없이도, 데이터에 근거한 다음 할 일을 매주 정하고 그것을 측정할 수 있게 한다. 에이전트는 질문에 답하는 것이 아니라, 종합해서 제안하고 실행 단계까지 적어 준다.

**핵심 결과 (프로토타입 출시 후 4주 기준, 모두 가정 — 7.4 참고):**
1. 에이전트의 기획 제안 중 팀이 실제로 채택해 작업에 반영한 것이 4주 동안 4건 이상. (채팅 기록에 채택 여부 표시)
2. 퍼널·이벤트 설계 제안의 80% 이상이 "어느 파일의 어느 함수에 어떤 이벤트를 심어라"까지 구체적이어서 추가 조사 없이 바로 구현할 수 있다. (수동 채점)
3. 제안이 인용한 수치가 Amplitude에서 확인했을 때 일치하는 비율 90% 이상.

## 5. 대상 세그먼트

사용자는 개발자 2명이다. 하려는 일에 따라 두 상황으로 나눈다.

**세그먼트 A — "다음에 무엇을 만들까"를 정해야 하는 개발자**
우선순위를 정할 근거가 필요하다. 예: "지금 가장 큰 이탈 지점이 어디고, 뭘 고치면 좋을까?", "메뉴 추천 기능을 더 키울 가치가 있나?"

**세그먼트 B — "그것을 어떻게 측정할까"를 설계해야 하는 개발자**
새 기능이나 가설을 측정할 퍼널과 이벤트를 설계하고 코드에 심어야 한다. 예: "장바구니 개선 효과를 보려면 퍼널을 어떻게 짜고, 어떤 이벤트를 어디에 추가해야 하나?"

**제약:**
- 사용자 2명. 인증, 권한, 멀티테넌시는 필요 없다.
- 코드 분석 예산은 Claude API 200달러. 코드베이스를 매번 통째로 읽으면 금방 소진된다.
- 프론트와 백엔드 코드를 이 폴더 하나에서 관리한다.

## 6. 가치 제안

### 세그먼트 A — 다음 할 일을 정해야 하는 개발자

- **누구:** 기획 결정을 내려야 하는 K-Bap 개발자
- **왜:** 다음 스프린트에 무엇을 할지 근거 있게 정하고 싶다. 하지만 데이터를 해석하고 가설을 세우는 일은 기획자의 일이고, 그 사람이 없다.
- **이전:** Amplitude를 열어 눈에 띄는 숫자를 보거나, 감으로 정한다. 왜 그 숫자가 나왔는지(어느 화면, 어느 동작인지) 알려면 코드를 다시 열어야 해서 깊이 들어가지 못한다.
- **방법:** 에이전트가 Amplitude 지표에서 이상 지점이나 기회를 찾고, 택사노미로 이벤트 의미를 확인하고, 코드로 실제 화면·동작 맥락을 확인한 뒤, "이 지점이 문제고, 이렇게 고치자, 효과는 이 지표로 보자"를 하나의 제안으로 낸다.
- **이후:** 매주 근거가 붙은 기획 제안을 받고, 채택·보류만 결정한다. 결정 기록이 채팅에 남는다.
- **대안:** Amplitude 콘솔 직접 분석, Amplitude 내장 AI, 일반 ChatGPT에 수치를 붙여 묻기. 우리를 택하는 이유: 우리 택사노미와 우리 코드를 알고 있어 "숫자"가 아니라 "우리 서비스의 어느 화면에서 무슨 일이 벌어지는지"를 근거로 제안한다.

**가치 제안 문장:** 기획자가 없는 개발팀이, 우리 데이터와 우리 코드를 아는 에이전트에게서 근거 있는 다음 할 일을 제안받고 결정만 한다.

### 세그먼트 B — 측정을 설계해야 하는 개발자

- **누구:** 새 기능의 퍼널과 이벤트 트래킹을 설계해야 하는 K-Bap 개발자
- **왜:** 기능을 만들었으면 효과를 측정해야 한다. 그러려면 퍼널 단계를 정의하고, 빠진 이벤트를 찾아, 코드 어디에 심을지 정해야 한다. 이 설계 능력이 팀에 없다.
- **이전:** 있는 이벤트로만 대충 본다. 새 이벤트는 이름을 즉흥적으로 짓고 적당한 곳에 심는다. 나중에 택사노미와 어긋나 데이터를 못 믿게 된다.
- **방법:** 에이전트가 측정하려는 가설을 받아, 택사노미에서 이미 있는 이벤트를 찾고, 코드에서 해당 화면의 컴포넌트와 핸들러를 찾아, "퍼널은 A→B→C, B는 기존 이벤트, C는 새 이벤트 `xxx`를 이 파일 이 함수에 추가"까지 설계안을 낸다.
- **이후:** 설계안을 보고 바로 구현한다. 택사노미와 코드가 어긋나지 않는다.
- **대안:** Amplitude 택사노미 거버넌스 기능(코드는 모름), IDE 검색(택사노미와 지표는 모름). 우리를 택하는 이유: 정의·코드·지표 세 가지를 함께 보고 설계하는 유일한 도구다.

**가치 제안 문장:** 가설만 말하면, 택사노미와 코드에 맞는 퍼널과 이벤트 설계를 코드 위치까지 받아 바로 구현한다.

## 7. 솔루션

### 7.1 핵심 흐름

1. 사용자가 채팅에 결정 과제나 가설을 입력한다. ("가장 큰 이탈 지점 찾아서 개선안 제안해줘", "장바구니 개선 효과 측정 설계해줘")
2. 에이전트가 계획을 세우고 필요한 만큼 세 소스를 반복 조회한다.
   - Amplitude MCP: 퍼널, 세그먼트, 리텐션 수치
   - 택사노미: 이벤트 정의와 속성
   - FE 코드: 이벤트 호출 지점, 해당 화면의 컴포넌트와 동작
3. 조회 결과를 종합해 제안을 쓴다. 제안은 반드시 **근거(수치와 코드 위치) → 제안 → 실행 단계 → 측정 방법** 순서다.
4. 사용자가 채택·보류·수정을 표시한다.
5. 대화, 도구 호출, 제안, 채택 여부를 MySQL에 저장한다.

### 7.2 첫 버전 필수 기능

- **채팅 UI와 저장:** 단일 대화창, 과거 대화 조회. 세션·메시지·도구 호출·제안·채택 여부를 MySQL에 저장. (핵심 결과 1 측정에 필요)
- **세 소스 통합 컨텍스트:**
  - 택사노미 로딩: 사용자가 전달한 파일을 읽어 이벤트별 정의를 제공
  - Amplitude MCP 연동: 공식 원격 MCP에 OAuth로 연결
  - FE 코드 탐색: GitHub 저장소 URL 등록 후 클론. 이벤트 호출 지점 검색과 화면 맥락 파악에 Claude API 사용
- **에이전트 루프:** 질문 하나에 도구를 여러 번 호출하고 중간 결과를 보고 다음 조회를 정하는 구조. 단발 조회·답변이 아니다.
- **제안 출력 형식 고정:** 근거 → 제안 → 실행 단계 → 측정 방법. 퍼널 설계 제안은 단계별 이벤트 이름과 기존/신규 여부, 신규 이벤트는 파일·함수 위치를 포함.
- **채택 표시:** 제안마다 채택/보류 버튼. 핵심 결과 1의 측정 수단.

### 7.3 기술

- 이 폴더에 프론트와 백엔드를 함께 둔다.
- 배포: 프론트는 GitHub Pages(정적 호스팅), 백엔드는 홈서버의 Docker 컨테이너. 프론트가 공개 인터넷을 거쳐 홈서버 백엔드를 호출하므로 백엔드는 HTTPS 공개 엔드포인트가 필요하다(터널 또는 리버스 프록시).
- 코드 분석: Claude API (200달러). grep으로 후보 파일을 좁힌 뒤 해당 파일만 모델에 보낸다. 코드 구조 요약(화면별 컴포넌트, 이벤트 호출 목록)은 한 번 만들어 캐시하고 커밋이 바뀌면 갱신한다.
- 추론·제안 생성: Claude 또는 GPT-6-luna. 설정으로 교체 가능하게 하고 프로토타입은 한 가지로 시작한다.
- Amplitude: 공식 원격 MCP. 조회 전용이며 이벤트 전송 경로가 아니다. (출처: https://amplitude.com/docs/mcp)

### 7.4 가정과 열린 질문

**가정 (검증 필요):**
- 핵심 결과 수치(채택 4건, 구체성 80%, 수치 일치 90%)는 작성자의 제안이다. 팀이 조정해야 한다.
- 세 소스를 종합한 LLM 제안이 개발자가 "채택할 만하다"고 느낄 수준이 된다. 이것이 제품의 가장 큰 가정이며, 프로토타입이 검증해야 할 핵심이다.
- 택사노미 문서가 이벤트별 정의와 속성을 충분히 담고 있다.
- FE 코드의 이벤트 호출이 grep으로 찾을 수 있는 일관된 패턴(공통 track 함수 등)을 쓴다.
- 코드 구조 요약을 캐시하면 질문당 코드 분석 비용이 예산 안에 들어온다.

**열린 질문:**
- 추론 모델을 Claude와 GPT-6-luna 중 무엇으로 시작할지. "제안 품질"을 어떻게 비교할지.
- 택사노미 전달 형식(스프레드시트, JSON, Amplitude export)?
- FE 저장소가 비공개일 때 GitHub 인증 방식?
- 에이전트가 먼저 제안하는 능동 모드(예: 매주 월요일 제안)를 첫 버전에 넣을지, 질문에 반응하는 모드로만 시작할지.
- 제안의 "근거"로 보여줄 코드 발췌 범위. 너무 길면 읽기 어렵고 너무 짧으면 믿기 어렵다.

## 8. 릴리스

**첫 버전 (프로토타입, 약 3~4주):**
- 채팅 UI + MySQL 저장 + 채택 표시
- 택사노미 로딩, Amplitude MCP, FE 저장소 1개 연결
- 에이전트 루프와 고정 제안 형식
- 두 가지 제안 유형: 기획 개선 제안(세그먼트 A), 퍼널·이벤트 설계 제안(세그먼트 B)

**다음 버전:**
- 능동 리포트: 캠페인 기간 등 지정한 기간 동안 매일 지표 변화와 해석을 보고서로 발송
- 신규 기능 제안 + Figma MCP 연동으로 UI 시안 생성
- Jira MCP 연동으로 채택된 제안을 이슈로 등록하고 다음 할 일 정리
- 추론 모델 비교와 선택
- 백엔드 코드 분석 확장

**명시적으로 하지 않는 것:**
- 사용자 인증, 권한 관리, 멀티테넌시 (사용자가 2명)
- 백엔드 코드 분석 (첫 버전은 FE 이벤트에 한정)
- Amplitude로의 이벤트 전송이나 택사노미 자동 수정 (조회 전용, 수정은 사람이)
- 코드 자동 수정이나 PR 생성 (위치와 코드를 제안만 한다)
- 세련된 UI. 동작하는 것이 먼저다.
