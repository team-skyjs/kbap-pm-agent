# PRD: 질문 마법사

작성일: 2026-10-15 · 상태: 초안 · 상위 PRD: `PRD-kbap-pm-agent.md`

## 1. 요약

보내기 버튼 옆에 "질문 다듬기" 버튼을 둔다. 누르면 백엔드가 LLM을 한 번 호출해 사용자의 질문을 에이전트가 한 번에 좋은 답을 낼 수 있는 형태로 고쳐 보여 주고, 사용자는 개선안과 원문 중 하나를 골라 보낸다. 지금은 PM이 질문을 어떻게 써야 좋은 제안이 나오는지 알기 어렵고, 모호한 질문은 조회 턴을 낭비하거나 부분 완료로 끝난다.

## 2. 배경

에이전트는 질문을 받아 택사노미·코드·Amplitude를 도구로 조회하고 제안을 만든다. 질문이 모호하면(기간 없음, 이벤트명 대신 일상어, 목표 지표 없음) 모델이 범위를 추측하며 턴을 쓰고, 10턴 상한에 걸려 부분 완료가 되거나 근거가 빠진다. 실제 첫 질문도 6턴·$1.60이 들었다. 질문을 보내기 전에 구체화하면 같은 비용으로 더 나은 답이 나오고, 사용자는 "좋은 질문의 모양"을 매번 눈으로 배운다.

지금 하는 이유: 재설계로 입력창과 상태 표현이 정리돼 버튼 하나와 비교 카드를 붙일 자리가 생겼고, 택사노미(45개 이벤트)와 대화 이력이 이미 서버에 있어 질문을 구체화할 재료가 갖춰졌다.

## 3. 목표

질문을 보내기 전에 구체화해 한 번에 쓸 만한 제안을 받게 한다.

측정: 개선안 채택 비율 하나만 잰다. 호출마다 원문·개선안·선택 결과를 DB에 남겨 언제든 "개선안을 본 횟수 중 개선안으로 보낸 비율"을 조회할 수 있게 한다. 목표 수치는 두지 않는다. 사용자 2명이라 통계가 아니라 참고값이고, 쓰면서 계속 둘지·고칠지 정한다.

## 4. 대상

**세그먼트 1 — PM 역할을 겸하는 개발자 2명(상위 PRD의 사용자와 같다).** 지표 이름과 기간을 머릿속으로는 알지만 매번 문장으로 옮기기 귀찮고, 어떤 표현이 에이전트에게 통하는지 모른다. 제약: 두 사람이라 사용량이 적어 통계가 작고, LLM 비용 누적 상한($200, 현 구현은 월 초기화 없이 누적 합산)이 있다.

첫 버전은 이 세그먼트만 본다. 나중에 들어올 다른 팀원도 같은 흐름을 쓴다.

## 5. 가치 제안

- **누가:** 질문을 자주 쓰는 PM.
- **왜:** 데이터 근거가 있는 기획 제안을 빨리 받고 싶다. 그런데 질문이 모호하면 답이 두루뭉술하거나 중간에 끊긴다.
- **지금은:** 한 줄로 던지고 결과를 본 뒤 다시 묻는다. 한 번에 1~2분과 $1 안팎이 들고, 두세 번 반복한다.
- **어떻게:** 버튼 하나로 질문을 "어떤 이벤트·기간·지표를 보고 무엇을 제안받을지"가 드러난 문장으로 바꿔 보여 주고, 원문과 나란히 놓아 고르게 한다.
- **그 뒤:** 첫 질문에서 쓸 만한 제안이 나오고, 반복 질문이 줄며, 사용자가 좋은 질문의 틀을 익힌다.
- **대안:** 도움말 페이지에 질문 예시를 적어 두기(읽지 않는다), 에이전트가 답하기 전에 되묻기(턴과 시간이 든다), 질문 템플릿 양식(자유도가 떨어진다). 마법사는 사용자가 원할 때만, 보내기 전에, 한 번의 싼 호출로 끝난다.

가치 제안 문장: 질문을 보내기 전에 버튼 하나로 에이전트가 가장 잘 답할 수 있는 형태로 고쳐 주고, 선택은 사용자가 한다.

## 6. 솔루션

### 6.1 흐름

1. 사용자가 입력창에 질문을 쓴다(비어 있으면 버튼 비활성).
2. "질문 다듬기" 버튼(보내기 왼쪽, 아이콘+라벨)을 누른다. 버튼이 진행 상태로 바뀌고 입력창은 잠긴다.
3. 입력창 위에 비교 카드가 뜬다. 왼쪽 원문, 오른쪽 개선안. 개선안 아래 "무엇이 달라졌나" 한 줄(예: 기간과 이벤트명을 명시).
4. 사용자는 "개선안으로 보내기" 또는 "원문으로 보내기" 중 하나를 누른다. 보내면 카드가 닫히고 평소 전송 흐름이 이어진다. ESC나 닫기는 카드만 닫고 원문을 입력창에 남긴다.
5. 개선안을 고르면 입력창 내용이 개선안으로 바뀐 채 전송된다(사용자가 전송 전에 손볼 수 있게 "입력창에 넣기"도 둔다).

### 6.2 첫 버전 필수 기능

- **백엔드 다듬기 API:** `POST /api/questions/refine`. 입력은 질문 텍스트(메시지와 같은 1~4000자 검증)와 대화 ID. 서버가 택사노미 이벤트명 목록과 그 대화의 최근 메시지 몇 개를 붙여 싼 모델을 한 번 호출한다. 출력은 개선된 질문 한 개와 변경 요약 한 줄(구조화 출력). 도구 호출 없음.
- **다듬기 규칙(시스템 프롬프트):** 사용자의 의도를 바꾸지 않는다. 기간·대상 이벤트(택사노미에 있는 실제 이름)·보고 싶은 지표·원하는 산출물(개선안인지 측정 설계인지)을 드러낸다. 없는 정보는 지어내지 않고 "최근 7일"처럼 합리적 기본값을 쓰되 요약에 그 사실을 적는다. 한국어, 두 문장 이내.
- **프론트 버튼과 비교 카드:** 입력창 옆 버튼, 입력창 위 카드, 이지선다 버튼 두 개, 변경 요약, 닫기. 키보드로 조작 가능. 진행·오류 상태(오류면 카드 대신 짧은 안내, 원문 유지).
- **기록:** 호출마다 원문·개선안·선택 결과(개선안/원문/취소)를 저장한다. 채택 비율 조회와 다듬기 규칙 개선의 근거가 된다. 화면에 보이지는 않는다(SQL 한 줄로 조회).
- **비용:** 호출당 비용을 기존 사용량 기록에 용도 "refine"으로 남겨 예산에 합산한다. 사용량 테이블의 용도 컬럼이 ENUM이라 값 추가는 `ALTER TABLE` 마이그레이션이 필요하며(기동 시 `CREATE TABLE IF NOT EXISTS`로는 바뀌지 않음), 앱 갱신보다 먼저 적용한다.

### 6.3 기술

- 모델은 환경변수 `REFINE_MODEL`로 정하고, 비어 있으면 코드 요약 모델(`CODE_SUMMARY_MODEL`, 현재 Claude Haiku 5.5)을 쓴다. 호출 1회, 도구 없음, 구조화 출력. 10건 샘플에서 재작성이 어색하면 Sonnet으로 올린다.
- 택사노미 이벤트명은 설정 테이블(`app_settings`의 `taxonomy` 키, 업로드 API가 저장하는 곳)에서 이름만 뽑아 넣는다(45개면 수백 토큰). 서버 파일로는 존재하지 않는다. 대화 이력은 최근 사용자·에이전트 메시지 각 2개까지, 본문은 앞 500자.
- 계약 변경: 엔드포인트 1개 추가. 응답 shape는 `{ refined: string, summary: string }`. 기록 테이블 1개 추가.

### 6.4 가정과 열린 질문

- 가정: 싼 모델로도 질문 재작성 품질이 충분하다. 10건 샘플로 확인한다.
- 열린 질문: 개선안을 편집한 뒤 보내는 경우를 "채택"으로 셀지. 첫 버전은 편집 후 전송도 채택으로 센다.
- 열린 질문: 마법사 결과를 다음 질문에도 학습 재료로 쓸지(채택 이력 반영 PRD와 함께 결정).

## 7. 릴리스

- **첫 버전:** 위 필수 기능 전부. 버튼은 항상 보이되 입력이 비면 비활성.
- **다음:** 확인 질문(빠진 정보를 되묻기), 개선안 여러 개, 자동 다듬기(보내기 전에 늘 제안). 사용 기록을 보고 결정.
- **하지 않는 것:** 자동으로 질문을 바꿔 보내기, 에이전트 실행 중 호출, 질문 외 텍스트(메모 등) 다듬기.
- **기간:** 계약·프롬프트 하루, 백엔드·프론트 병행 하루, QA 반나절.
