# PRD: 접근 제한 (Cloudflare Access 뒤로 서비스 이동)

작성일: 2026-10-15 · 상태: **진행** (2026-10-15 보류 → 같은 날 재개. 사용자 결정: GitHub Pages 프로젝트 사이트가 조직 공용 출처라 저장된 공유 토큰이 다른 Pages 프로젝트에 노출될 수 있고, 공유 토큰은 사용자 구분·만료가 없어 정식 보호로 Cloudflare Access를 적용한다) · 상위 PRD: `PRD-kbap-pm-agent.md`

## 1. 요약

K-Bap PM Agent의 프론트와 API를 한 호스트명 아래로 모으고 Cloudflare Access로 허용된 사람만 들어오게 한다. 지금은 GitHub Pages 주소와 API 주소가 모두 공개되어 있어 누구나 화면을 열고 LLM 크레딧을 쓸 수 있다. 첫 운영 배포가 끝난 지금, 실제 사용을 시작하기 전에 막아야 한다.

## 3. 배경

첫 프로토타입은 프론트를 GitHub Pages(team-skyjs.github.io/kbap-pm-agent/)에, 백엔드를 홈서버 컨테이너(<운영 API 호스트명>)에 배포했다. 레포를 공개로 바꾸면서 Pages가 가능해졌지만, 그 결과 두 가지가 열렸다.

- 화면 주소를 아는 누구나 접속해 대화와 설정을 볼 수 있다.
- API가 인증 없이 열려 있어, 주소를 알면 메시지를 보내 200달러 LLM 예산을 소진시킬 수 있다. 프론트는 네트워크 요청에서 API 주소를 숨길 수 없다.

왜 지금인가: 운영 배포가 막 끝났고 실제 키를 넣어 첫 질문을 하기 직전이다. 사용이 시작되기 전에 막는 것이 가장 싸다. 홈서버는 이미 Cloudflare 터널 뒤에 있어 Access를 켜는 데 추가 인프라가 필요 없다.

GitHub Pages에는 Access를 걸 수 없다. 커스텀 도메인을 Cloudflare로 프록시해도 원래 github.io 주소가 그대로 열려 우회된다. 비공개 Pages는 GitHub Enterprise 전용이다. 따라서 프론트를 홈서버로 옮겨야 한다.

## 4. 목표

**목표:** 허용 목록에 있는 사람만 화면과 API에 닿게 한다. 그 외 요청은 로그인 화면에서 멈춘다. 팀은 LLM 예산이 남이 아니라 자기 질문에만 쓰인다고 믿을 수 있다.

**핵심 결과 (적용 후 1주 기준, 수치는 가정 — 7.4 참고):**
1. 허용 목록 밖에서 보낸 API 요청이 백엔드에 도달하는 수 0건. (Cloudflare Access 로그와 백엔드 요청 로그 대조)
2. 허용된 두 사람이 이메일 로그인 한 번으로 화면 진입 → 질문 → 제안 확인까지 추가 조작 없이 완료. (수동 확인)
3. 옛 GitHub Pages 주소와 옛 API 직접 호출 경로가 모두 닫힘. (접속 시 404 또는 Access 로그인)

## 5. 대상 세그먼트

**세그먼트 A — 서비스를 쓰는 팀원 (개발자 2명)**
매일 질문하고 제안을 받는 사람. 로그인이 귀찮으면 안 쓰게 되므로 한 번 로그인하면 오래 유지되어야 한다.

**세그먼트 B — 예산과 데이터를 지키는 운영자 (같은 2명 중 인프라 담당)**
LLM 예산, 저장소 토큰, Amplitude 연결, 대화 기록이 밖으로 새지 않게 해야 한다. 코드에 인증 로직을 넣고 유지하는 부담은 피하고 싶다.

**제약:**
- 사용자 2명. 역할·권한 구분 없음. 허용 목록 하나면 된다.
- Cloudflare 무료 플랜(Zero Trust 50명 한도) 안에서 끝낸다.
- 홈서버의 기존 터널(cloudflared, 대시보드 관리형)과 monitor-net 네트워크를 그대로 쓴다.

## 6. 가치 제안

### 세그먼트 A — 서비스를 쓰는 팀원

- **누구:** 매일 PM 에이전트에 질문하는 개발자
- **왜:** 내 대화와 설정을 남이 볼 수 없어야 안심하고 쓴다. 하지만 매번 비밀번호를 넣는 것은 싫다.
- **이전:** 주소를 아는 누구나 들어올 수 있다. 대화 기록과 저장소 설정이 노출된다.
- **방법:** 처음 한 번 이메일로 일회용 PIN 로그인. 이후 세션이 유지되어 그냥 접속한다.
- **이후:** 공개 주소가 사라지고, 내 대화는 허용된 두 사람만 본다.
- **대안:** 앱 안에 자체 로그인 구현. 우리를 택하는 이유: 코드 변경 없이 인프라에서 끝나고, 세션·PIN·로그아웃을 직접 만들 필요가 없다.

**가치 제안 문장:** 한 번 이메일로 로그인하면, 내 PM 에이전트는 팀만 보는 도구가 된다.

### 세그먼트 B — 예산과 데이터를 지키는 운영자

- **누구:** 홈서버와 LLM 예산을 관리하는 개발자
- **왜:** 예산이 외부 호출로 새면 제품 검증이 멈춘다. 그러나 인증 코드를 백엔드에 넣고 토큰을 관리하는 일은 늘리고 싶지 않다.
- **이전:** API가 열려 있다. 선택 장치(공유 토큰)가 있지만 꺼져 있고, 켜도 프론트와 토큰을 맞춰야 한다.
- **방법:** 프론트와 API를 한 호스트명에 두고 Cloudflare Access 하나로 막는다. Access를 통과하지 못한 요청은 홈서버에 닿지 않는다.
- **이후:** 백엔드 코드에 인증이 없어도 안전하다. 허용 목록 수정은 대시보드에서 한다. CORS 설정도 사라진다.
- **대안:** 공유 토큰 유지, 자체 로그인, VPN(Tailscale)으로만 접속. 우리를 택하는 이유: 토큰은 유출되면 끝이고 VPN은 폰에서 불편하다. Access는 둘의 단점이 없고 이미 쓰는 Cloudflare 안에 있다.

**가치 제안 문장:** 인증 코드 한 줄 없이, 허용된 이메일 밖에서는 API에 닿을 수 없다.

## 7. 솔루션

### 7.1 핵심 흐름

1. 사용자가 `https://<운영 API 호스트명>/`를 연다.
2. Cloudflare Access가 로그인 화면을 보여 준다. 이메일 입력 → 일회용 PIN → 통과.
3. 터널은 지금처럼 백엔드 컨테이너 하나로 보낸다. 백엔드가 `/api/*`는 API로, 나머지는 빌드된 프론트 정적 파일로 응답한다.
4. 같은 출처라 프론트의 API 호출은 상대 경로 `/api/...`다. CORS 없음.
5. 세션이 유지되는 동안(기본 24시간, 조정 가능) 재로그인 없이 쓴다.

### 7.2 첫 버전 필수 기능

- **단일 컨테이너 서빙:** 백엔드 이미지가 프론트 빌드 산출물을 담고 `/`에서 정적 파일로 제공한다(서버에 별도 웹 서버가 없고 다른 앱도 같은 방식이라는 2026-10-15 사용자 결정). Vite base를 `/`로, API 주소를 상대 경로로. 해시 라우팅 유지.
- **터널 규칙:** 변경 없음. 운영 호스트명 → 백엔드 컨테이너 하나.
- **Access 애플리케이션:** 호스트 `<운영 API 호스트명>` 전체. 정책 "이메일이 허용 목록에 있음". 로그인은 일회용 PIN.
- **배포 통합:** 이미지 하나를 레포 루트 컨텍스트로 빌드한다(1단계 프론트 빌드, 2단계 백엔드 + 정적 파일). 배포 한 번에 둘 다. 트리거 경로에 `frontend/**`를 포함해 프론트만 바뀐 병합도 배포되게 한다(현재는 백엔드·배포 파일 변경에만 돈다).
- **옛 경로 폐쇄:** Pages 워크플로우 삭제, Pages 사이트 비활성화. 백엔드 CORS 허용 목록에서 github.io 제거.

### 7.3 기술

- 정적 서빙: FastAPI StaticFiles를 `/`에 마운트(API 라우트가 먼저 매칭). SPA라 404 → index.html 처리는 해시 라우팅 덕에 불필요. 캐시는 ETag 재검증으로 충분.
- 터널은 토큰 기반 원격 관리형이라 ingress 변경은 Zero Trust 대시보드에서 한다. 로컬 설정 파일 없음.
- 백엔드 코드 변경은 정적 마운트 한 곳. 공유 토큰 장치(ACCESS_TOKEN)는 7.5 참고.
- 운영 검사(check_b8)와 외부 모니터링은 Access에 막히므로 Cloudflare 서비스 토큰으로 호출하거나 홈서버 내부에서 돌린다.

### 7.4 가정과 열린 질문

**가정 (검증 필요):**
- 핵심 결과 수치(0건, 1주)는 작성자 제안이다.
- 대시보드 관리형 터널이 같은 호스트명에 경로 기반 규칙 두 개를 허용한다. (같은 홈서버의 다른 서비스가 이미 같은 방식을 쓰고 있어 가능성 높음)
- 일회용 PIN 로그인 세션이 폰 브라우저에서도 24시간 유지된다.
- Access가 SSE 스트리밍 응답(최대 170초)을 끊지 않는다. Cloudflare 프록시의 100초 제한은 이미 SSE 설계에서 고려됨.

**열린 질문:**
- 허용 목록 이메일 2개는 무엇인가. (사용자만 안다)
- 세션 길이를 24시간으로 할지 더 길게 할지.
- check_b8을 서비스 토큰으로 돌릴지, 홈서버 내부 실행으로 바꿀지.
- 공유 토큰 코드(ACCESS_TOKEN)를 이번에 제거할지 남길지.
- Amplitude OAuth 콜백 URL(`/api/integrations/amplitude/callback`)이 Access 뒤에서도 동작하는지. 승인 후 브라우저가 콜백으로 돌아올 때 이미 로그인 상태이므로 통과할 것으로 보지만 확인 필요.

### 7.4b 재개 배경 (2026-10-15)

보류 뒤 공유 토큰으로 운영하던 중 두 가지가 확인됐다. (1) GitHub Pages 프로젝트 사이트는 조직 전체가 한 출처를 공유하므로, 같은 조직의 다른 Pages 프로젝트 스크립트가 브라우저 저장소의 토큰을 읽을 수 있다. (2) 공유 토큰은 사용자 구분·만료·즉시 차단이 없다. 둘 다 프론트를 전용 출처로 옮기고 Access로 막으면 사라진다. 이 PRD를 진행으로 되돌리고, 보관 브랜치의 구현을 main에 합쳐 재개한다.

### 7.5 전환 장치: 공유 접근 토큰 (Access 운영 검증 전까지)

Cloudflare Access가 검증되기 전에도 API가 공개 상태로 남지 않도록 공유 접근 토큰을 운영 필수로 켜 둔다(2026-10-15 적용, 배포가 토큰 없으면 실패). 전환 중에는 Access와 토큰이 함께 켜져 있고, 새 출처에서는 설정 화면에 토큰을 한 번 다시 입력한다.

- 백엔드 환경변수 ACCESS_TOKEN에 무작위 값을 두면 헬스와 Amplitude 콜백을 제외한 모든 API가 `Authorization: Bearer <값>`을 요구하고, 없거나 다르면 401(공통 에러 형식)로 거부한다. 값은 GitHub Secret으로만 관리하고 배포 시 env에 들어간다.
- 프론트는 설정 화면에 입력한 토큰을 브라우저 저장소에만 두고 모든 요청에 붙인다. 번들·소스에 값이 없다.
- 한계: 사용자 구분·만료·로그아웃 없음. 새면 Secret 교체 → 재배포 → 두 사람 재입력. 이 한계 때문에 정식 보호는 Cloudflare Access다.
- 종료 조건: Access 적용·검증(사용자 스토리 2 통과) 후 배포의 토큰 필수 검사를 제거하고 Secret을 비워 끈다. 그 뒤로는 Access만 남는다.
