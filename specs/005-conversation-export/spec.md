# Feature Specification: 대화 전체 내보내기

**Feature Branch**: `feat/conversation-export`

**Created**: 2026-10-17

**Status**: Draft

**Input**: User description: "docs/prd/PRD-conversation-export.md — 대화 한 건을 처음부터 끝까지 PDF(브라우저 인쇄)나 Markdown 파일로 저장해 공유한다. 지금은 인쇄하면 화면에 보이는 범위만 찍힌다. 내보내기 건수와 형식만 기록한다."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 대화 전체를 PDF로 인쇄한다 (Priority: P1)

개발자가 대화 화면의 "내보내기"에서 PDF를 고르면 브라우저 인쇄 대화상자가 열린다. 미리보기와 결과에는 대화 제목·날짜 머리글 아래 첫 메시지부터 마지막 메시지까지 모두 담긴다. 사이드바·입력창·조작 버튼은 빠진다. 제안 카드는 네 절이 모두 펼쳐진 채로, 차트는 완성된 그림으로 담긴다. 다크 테마를 쓰고 있어도 인쇄는 밝은 배경이다.

**Why this priority**: 사용자가 실제로 겪은 문제(화면 범위만 인쇄됨)를 고친다. 결정 근거 공유의 기본 경로다.

**Independent Test**: 화면 높이보다 긴 대화(차트·제안 카드 포함)를 열고 PDF로 인쇄해, 미리보기 페이지에 모든 메시지와 카드의 네 절, 차트가 있는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 화면보다 긴 대화, **When** 내보내기 → PDF, **Then** 인쇄 결과에 모든 메시지가 순서대로 있다
2. **Given** 제안 카드의 접힌 절, **When** 인쇄, **Then** 근거·제안·실행 단계·측정 방법이 모두 펼쳐져 인쇄되고, 인쇄가 끝나면 화면의 접힘 상태가 원래대로 돌아온다
3. **Given** 차트가 있는 답변, **When** 인쇄, **Then** 차트가 인쇄 폭 안에 완성된 상태로 찍히고, 인쇄가 끝나면 화면 차트가 원래 크기·색으로 돌아온다
4. **Given** 다크 테마, **When** 인쇄, **Then** 배경은 흰색이고 글자·차트는 밝은 테마 색이다
5. **Given** 인쇄 결과, **When** 본다, **Then** 사이드바·입력창·다듬기 카드·버튼·도구 진행 행·사용량 줄(모델·토큰·비용)은 없고, 제안 카드의 각 절(머리·근거·제안·실행 단계·측정 방법)·차트·코드 블록·표 행은 페이지 경계에서 중간에 잘리지 않는다(한 페이지보다 큰 경우 제외). 네 절을 다 편 카드는 한 쪽을 넘을 수 있어 절 단위로 나뉜다. 긴 메시지 본문은 쪽 경계에서 나뉠 수 있다(통째로 다음 쪽으로 밀어 빈칸을 만들지 않는다). 긴 코드·표는 가로로 넘치지 않는다

### User Story 2 - 대화 전체를 Markdown 파일로 받는다 (Priority: P1)

개발자가 "내보내기"에서 Markdown을 고르면 `대화제목-YYYYMMDD.md` 파일이 바로 내려받아진다. 파일에는 다음이 순서대로 담긴다.
- 대화 머리글
- 메시지별 역할·시각·본문(에이전트 답변은 원래 Markdown 그대로)
- 제안 카드(제목·채택 상태, 근거·제안·실행 단계·측정 방법 네 절)
- 차트 데이터 블록 원문

서버 호출 없이 화면에 이미 있는 데이터로 만든다.

**Why this priority**: 문서로 옮기는 사용자의 경로다. PDF와 독립적으로 가치가 있다.

**Independent Test**: 제안 카드·차트·표가 있는 대화를 Markdown으로 내려받아 파일을 열고, 형식 규격(contracts/export-markdown.md)과 비교한다.

**Acceptance Scenarios**:

1. **Given** 대화, **When** 내보내기 → Markdown, **Then** 파일이 내려받아지고 이름이 `대화제목-YYYYMMDD.md`(내보낸 날짜) 형식이다
2. **Given** 표·코드·chart 블록이 든 답변, **When** 파일을 연다, **Then** 답변 본문이 원래 Markdown 그대로라 표·코드·chart 블록이 살아 있다
3. **Given** 채택·보류·미정 제안, **When** 파일을 연다, **Then** 각 제안에 상태 라벨과 네 절이 있다
4. **Given** 제목에 파일 이름으로 못 쓰는 문자(`/` 등)가 있거나 제목이 없음, **When** 내려받는다, **Then** 문제 문자는 바뀌고, 제목이 없으면 정해진 이름으로 대체된다
5. **Given** 내보낸 파일, **When** 내용을 검색, **Then** 앱의 API 주소·호스트명이 없다(답변 본문에 사용자가 쓴 내용은 그대로)

### User Story 3 - 내보내기 기록이 남는다 (Priority: P2)

팀이 언제든 내보내기 건수와 형식을 조회 한 줄로 본다. PDF·Markdown을 시작할 때마다 대화와 형식이 기록된다. 기록이 실패해도 내보내기는 진행된다.

**Why this priority**: PRD의 유일한 측정이다. 화면에는 보이지 않는다.

**Independent Test**: PDF 1회, Markdown 2회 내보낸 뒤 형식별 건수 조회 결과가 1과 2인지 본다.

**Acceptance Scenarios**:

1. **Given** PDF 선택, **When** 인쇄 대화상자가 열림, **Then** 형식 "PDF" 기록이 하나 생긴다(실제 저장 여부와 무관)
2. **Given** Markdown 선택, **When** 내려받기 시작, **Then** 형식 "Markdown" 기록이 하나 생긴다
3. **Given** 기록 저장 실패, **When** 내보내기, **Then** 인쇄·내려받기는 정상 진행된다

---

### Edge Cases

- 메시지가 0개인 대화: "내보내기" 버튼이 비활성이다
- 에이전트가 답을 만드는 중: 버튼이 비활성이다(반쯤 만든 답이 들어가지 않게)
- 실패한 에이전트 메시지: PDF는 화면 그대로, Markdown은 "실패" 표시와 오류 코드를 남긴다
- 아주 긴 대화(수백 메시지): 동작은 같다. 인쇄 미리보기 지연은 측정하지 않는다(PRD 가정)
- 한 페이지보다 긴 메시지나 카드: 페이지 경계에서 나뉜다(끊김 방지는 가능할 때만)
- 인쇄 대화상자를 취소: 화면 상태(접힘, 차트)가 원래대로 돌아오고, 기록은 이미 남아 있다
- 키보드만: 버튼과 두 선택지에 도달·실행할 수 있다

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 대화 화면 상단 바에 "내보내기" 버튼이 있고 PDF·Markdown 두 선택지를 연다. 메시지가 0개이거나 에이전트 실행 중이면 비활성이다. 키보드로 조작할 수 있다
- **FR-002**: PDF 선택은 브라우저 인쇄 대화상자를 연다. 인쇄 매체에서만 화면 높이 고정과 스크롤 영역을 풀어 대화 전체가 문서 흐름에 놓인다
- **FR-003**: 인쇄 결과는 사이드바·입력창·다듬기 카드·조작 버튼·도구 진행 행·사용량 줄(모델·토큰·비용)을 숨기고(Markdown이 비용을 빼는 것과 같은 기준), 대화 제목·생성일·내보낸 날짜 머리글을 붙인다
- **FR-004**: 인쇄 중에는 제안 카드의 모든 절이 펼쳐지고, 인쇄가 끝나면 화면의 접힘 상태가 복원된다
- **FR-005**: 인쇄 중 차트는 애니메이션 없이 인쇄 폭에 맞춰 밝은 테마 색으로 다시 그려지고, 끝나면 화면 상태로 돌아온다
- **FR-006**: 인쇄는 테마와 무관하게 밝은 배경·밝은 테마 색이다
- **FR-007**: 제안 카드의 각 절·차트·코드 블록·표 행은 페이지 경계에서 잘리지 않고, 메시지 본문은 쪽 경계에서 나뉠 수 있다(빈 쪽을 만들지 않음). 코드·표는 가로로 넘치지 않는다
- **FR-008**: Markdown 선택은 서버 호출 없이 화면의 대화 데이터로 파일을 만들어 내려받는다. 형식은 규격 하나를 따른다(contracts/export-markdown.md)
- **FR-009**: 내보낸 파일과 인쇄 머리글에는 앱의 API 주소·호스트명이 들어가지 않는다
- **FR-010**: PDF·Markdown 시작마다 대화와 형식을 기록하고, 기록 실패는 내보내기를 막지 않는다
- **FR-011**: 새 의존성, 서버 PDF 생성, 헤드리스 브라우저, PDF 라이브러리를 쓰지 않는다
- **FR-012**: 기존 화면 동작과 계약은 바뀌지 않는다(기록 엔드포인트 하나만 추가)

### Key Entities

- **내보내기 기록**: 대화, 형식(PDF·Markdown), 시각
- **Markdown 내보내기 파일**: 머리글, 메시지 목록(역할·시각·본문), 제안 카드(제목·상태·네 절), 파일 이름

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 화면 높이의 3배 이상인 대화를 PDF로 인쇄하면 모든 메시지·제안 카드 네 절·차트가 결과에 있다(Chrome 인쇄 미리보기, 수동)
- **SC-002**: Markdown 파일이 형식 규격의 모든 항목을 만족한다(자동 검사)
- **SC-003**: 형식별 내보내기 건수를 조회 한 줄로 언제든 볼 수 있다(목표 수치 없음)
- **SC-004**: 인쇄 매체 자동 검사에서 숨겨야 할 요소가 모두 숨고 메시지 영역이 스크롤 영역이 아니다
- **SC-005**: 기존 회귀 없음(기존 모듈·UI 검사 통과)

## Assumptions

- 사용자는 Chrome 인쇄 대화상자에서 "PDF로 저장"을 직접 고른다. 자동 저장은 브라우저가 허용하지 않는다(PRD 6.4)
- 대화는 수십 메시지 수준이다
- 대화 상세 응답은 메시지를 통째로 주고 화면은 가상 스크롤이 없어 대화 전체가 이미 화면에 있다(PRD 2절)
- Markdown에는 최종 전송된 메시지만 넣는다. 다듬기 선택 흔적과 도구 호출 목록은 넣지 않는다(PRD 열린 질문의 첫 버전 기본값)
- 공유 링크, 메시지 범위 선택, 이미지 내보내기, 외부 서비스 전송은 범위 밖이다(PRD 7절)
- PRD는 "백엔드 변경 없음, 기존 로그 경로로 기록"이라고 했지만 조회 가능한 기존 로그 경로가 없다. 그래서 기록만을 위한 최소 엔드포인트 하나를 둔다(ADR-31)
