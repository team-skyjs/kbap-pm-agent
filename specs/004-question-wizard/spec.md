# Feature Specification: 질문 마법사

**Feature Branch**: `feat/question-wizard`

**Created**: 2026-10-15

**Status**: Draft

**Input**: User description: "docs/prd/PRD-question-wizard.md — 보내기 옆 '질문 다듬기' 버튼을 누르면 서버가 모델을 한 번 호출해 질문을 에이전트가 한 번에 잘 답할 수 있는 형태로 고쳐 보여 주고, 사용자는 개선안과 원문 중 하나를 골라 보낸다. 선택 결과를 기록해 채택 비율을 본다. 다듬기 모델은 샘플 10건 비교로 정한다."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 질문을 다듬어 고르고 보낸다 (Priority: P1)

사용자가 입력창에 질문을 쓰고 "질문 다듬기"를 누른다. 잠시 진행 표시가 보인 뒤 입력창 위에 비교 카드가 뜬다. 원문과 개선안이 나란히 있고 개선안 아래에 무엇이 달라졌는지 한 줄이 있다. 사용자는 다음 중 하나를 고른다.
- "개선안으로 보내기"
- "원문으로 보내기"
- "입력창에 넣기"(개선안을 입력창에 넣고 손본 뒤 직접 보냄)
- 닫기(원문 유지)

**Why this priority**: 사용자가 보는 기능의 전부다. 이것만으로도 가치가 있다(다듬기 품질 개선·기록·모델 선정은 그 위에 얹힌다).

**Independent Test**: 시연 모드에서 질문을 쓰고 버튼을 누른다. 비교 카드가 뜨는지, 네 가지 선택이 각각 기대대로 동작하는지(보내기 두 가지는 대화에 메시지가 생김, 입력창에 넣기는 전송 없음, 닫기는 원문 유지) 확인한다.

**Acceptance Scenarios**:

1. **Given** 입력창이 비어 있음, **When** 화면을 본다, **Then** "질문 다듬기" 버튼은 보이지만 비활성이다
2. **Given** 질문이 있음, **When** 버튼을 누른다, **Then** 버튼이 진행 상태가 되고 입력창이 잠기며, 끝나면 비교 카드가 입력창 위에 뜬다
3. **Given** 비교 카드, **When** "개선안으로 보내기", **Then** 카드가 닫히고 개선안이 메시지로 전송되어 평소 진행 표시가 이어진다
4. **Given** 비교 카드, **When** "원문으로 보내기", **Then** 원문이 그대로 전송된다
5. **Given** 비교 카드, **When** "입력창에 넣기", **Then** 입력창 내용이 개선안으로 바뀌고 전송되지 않는다
6. **Given** 비교 카드, **When** ESC나 닫기, **Then** 카드만 닫히고 원문이 입력창에 남는다
7. **Given** 에이전트가 답을 만드는 중, **When** 화면을 본다, **Then** "질문 다듬기" 버튼은 비활성이다
8. **Given** 다듬기 실패(모델 오류·예산 초과 등), **When** 결과가 온다, **Then** 카드 대신 짧은 안내가 보이고 원문이 입력창에 남는다
9. **Given** 키보드만, **When** 버튼 → 카드 → 선택까지 조작, **Then** 모두 가능하고 카드가 열리면 포커스가 카드로, 닫히면 입력창으로 돌아간다

### User Story 2 - 다듬은 질문이 에이전트가 답하기 좋은 모양이다 (Priority: P1)

사용자는 개선안에서 다음을 본다.
- 무엇을 하는지: 기간, 대상 이벤트(택사노미의 실제 이름), 보고 싶은 지표, 원하는 산출물(개선안인지 측정 설계인지)이 드러난다.
- 하지 않는 것: 원래 의도가 바뀌지 않는다. 원문에 없는 정보를 지어내지 않는다.
- 기본값: 기본값을 넣었으면 요약에 그 사실이 적혀 있다.
- 모양: 개선안은 한국어 두 문장 이내다.

**Why this priority**: 개선안이 쓸모없으면 사용자는 원문만 고른다. US1과 함께 첫 가치를 만든다.

**Independent Test**: 이벤트 이름 없이 일상어로 쓴 질문, 기간 없는 질문, 이미 구체적인 질문, 직전 대화를 잇는 후속 질문 네 가지를 다듬어 규칙 위반이 없는지 사람이 본다.

**Acceptance Scenarios**:

1. **Given** "스캔 이탈 왜 많아?"(기간·이벤트 없음), **When** 다듬는다, **Then** 개선안에 실제 이벤트 이름과 기간이 들어가고 요약에 "기간을 정함(원문에 없음)" 같은 표시가 있다
2. **Given** 택사노미에 없는 대상을 묻는 질문, **When** 다듬는다, **Then** 없는 이벤트 이름을 지어내지 않고 사용자의 말을 유지한다
3. **Given** 직전 대화가 있는 후속 질문("그걸 주 단위로"), **When** 다듬는다, **Then** 직전 대화의 대상이 개선안에 들어간다
4. **Given** 이미 구체적인 질문, **When** 다듬는다, **Then** 의미가 바뀌지 않고 요약이 "거의 그대로"임을 알린다

### User Story 3 - 선택 결과가 남아 채택 비율을 본다 (Priority: P2)

팀이 언제든 "개선안을 본 횟수 중 개선안으로 보낸 비율"을 조회한다. 다듬기 호출마다 원문·개선안·요약·쓴 모델·선택 결과(개선안·원문·취소)·시각이 남는다. 다듬기 비용은 기존 사용량에 합산된다.

**Why this priority**: PRD의 유일한 측정이다. 화면에는 보이지 않고 조회로만 쓴다.

**Independent Test**: 시연 모드에서 네 가지 선택을 한 번씩 하고, 기록 테이블에서 선택 값과 채택 비율 조회 한 줄의 결과를 확인한다.

**Acceptance Scenarios**:

1. **Given** 다듬기 1회와 "개선안으로 보내기", **When** 기록을 조회, **Then** 그 행의 선택이 "개선안"이고 시각이 있다
2. **Given** "입력창에 넣기" 후 편집해서 보냄, **When** 조회, **Then** 선택이 "개선안"으로 남는다(편집 후 전송도 채택으로 센다)
3. **Given** 닫기, **When** 조회, **Then** 선택이 "취소"다
4. **Given** 다듬기 호출, **When** 사용량을 본다, **Then** 용도 "다듬기"로 비용이 기록되고 예산 합계에 들어간다
5. **Given** 선택 기록 저장이 실패, **When** 사용자가 보내기를 누름, **Then** 전송은 정상 진행된다

---

### User Story 4 - 다듬기 모델을 비교로 정한다 (Priority: P2)

팀이 실제 질문 유형을 닮은 샘플 10건을 싼 모델과 중간 모델로 각각 다듬어 나란히 놓고 네 항목을 채점한다. 항목은 의도 보존, 실제 이벤트 이름 사용, 기간과 지표 명시, 문장 자연스러움이다. 그 결과로 다듬기 모델 설정값을 정한다.

**Why this priority**: 품질과 비용의 균형을 근거로 정한다(사용자 결정). 기능은 기본 모델로 먼저 동작한다.

**Independent Test**: 비교표 파일에 샘플 10건 × 모델 2개 결과와 항목별 점수, 합계, 결정이 있다.

**Acceptance Scenarios**:

1. **Given** 샘플 10건, **When** 두 모델로 다듬는다, **Then** 같은 입력에 대한 두 결과가 나란히 기록된다
2. **Given** 채점 결과, **When** 결정 규칙을 적용, **Then** 다듬기 모델 설정값이 정해지고 근거가 비교표에 남는다

---

### Edge Cases

- 질문이 4000자를 넘거나 공백뿐일 때: 버튼은 비활성이고, 서버도 같은 규칙으로 거절한다
- 다듬는 동안 사용자가 다른 대화로 옮길 때: 결과는 버리고 카드를 띄우지 않으며 선택 기록은 남기지 않는다(호출 기록 행은 선택 없음으로 남는다)
- 개선안이 원문과 같을 때: 카드는 그대로 보이고 요약이 그 사실을 알린다
- 택사노미가 아직 업로드되지 않았을 때: 이벤트 이름 없이 기간·지표·산출물만 다듬는다
- 택사노미 이름이 4,000자를 넘을 때: 앞부분만 참고하고 변경 요약 끝에 그 사실을 붙인다
- 새 대화(이력 없음)에서 누를 때: 이력 없이 다듬는다
- 예산 상한에 닿았을 때: 다듬기를 거절하고 짧은 안내를 보이며 원문은 유지한다
- 같은 질문을 연달아 다듬을 때: 매번 새 호출이고 새 기록이다(재사용 없음)

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 입력창 옆에 "질문 다듬기" 버튼이 있다. 입력이 비었거나 에이전트 실행 중이면 비활성이다
- **FR-002**: 버튼을 누르면 서버가 모델을 한 번 호출해(도구 없음) 개선된 질문 하나와 변경 요약 한 줄을 돌려준다. 입력 검증은 메시지 전송과 같다(1~4000자)
- **FR-003**: 서버는 다듬을 때 택사노미의 이벤트 이름 목록(최대 4,000자, 넘으면 앞부분만 쓰고 요약에 표시)과 해당 대화의 최근 사용자·에이전트 메시지 각 2개(본문 앞 500자)를 참고한다
- **FR-004**: 다듬기 규칙은 다음과 같다. 의도를 바꾸지 않는다. 기간·실제 이벤트 이름·지표·산출물 종류를 드러낸다. 없는 정보는 지어내지 않는다. 기본값을 썼으면 요약에 적는다. 한국어 두 문장 이내다
- **FR-005**: 비교 카드는 원문·개선안·변경 요약과 동작 세 개(개선안으로 보내기, 원문으로 보내기, 입력창에 넣기), 닫기(ESC 포함)를 갖는다. 키보드로 모두 조작할 수 있다
- **FR-006**: 다듬기 실패 시 카드 대신 짧은 안내를 보이고 원문을 유지한다
- **FR-007**: 다듬기 호출마다 원문·개선안·요약·모델·선택 결과(개선안·원문·취소)·시각을 저장한다. 편집 후 전송도 개선안 채택으로 센다
- **FR-008**: 다듬기 비용은 기존 사용량 기록에 용도 "다듬기"로 남고 예산 합계와 예산 상한 검사에 포함된다
- **FR-009**: 선택 기록 실패가 메시지 전송을 막지 않는다
- **FR-010**: 다듬기 모델은 설정 하나로 정하고, 비어 있으면 코드 요약 모델을 쓴다. 코드 변경 없이 바꿀 수 있다
- **FR-011**: 시연 모드에서 다듬기는 모델을 부르지 않고 정해진 예시 결과를 돌려주며, 기록은 실제로 남긴다
- **FR-012**: 기존 메시지 전송·응답 형식은 바뀌지 않는다(다듬기는 전송 전 단계다)

### Key Entities

- **다듬기 기록**: 대화(없을 수 있음), 원문, 개선안, 변경 요약, 쓴 모델, 선택 결과(없음·개선안·원문·취소), 만든 시각, 고른 시각
- **다듬기 사용량**: 기존 사용량 기록의 한 행(용도 "다듬기", 모델, 토큰, 비용)

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 버튼을 누른 뒤 비교 카드가 뜰 때까지 보통 5초 이내다(실제 모델, 10회 중앙값)
- **SC-002**: 채택 비율을 조회 한 줄로 언제든 볼 수 있다(목표 수치는 두지 않는다. PRD 3절)
- **SC-003**: 샘플 10건 비교표가 남고, 그 결정에 따라 다듬기 모델 설정값이 정해져 있다
- **SC-004**: 다듬기 1회 비용이 질문 1회 비용의 1% 이하다(사용량 기록으로 확인)
- **SC-005**: 기존 기능 회귀가 없다(기존 모듈 검사·UI 검사 통과, 질문 → 제안 → 채택 흐름 유지)

## Assumptions

- 사용자는 기존 개발자 2명이다. 사용량이 적어 채택 비율은 통계가 아니라 참고값이다
- 싼 모델로도 다듬기 품질이 충분하다는 것은 US4 비교로 확인한다(PRD 6.4)
- 택사노미는 기존 업로드 기능이 저장한 이벤트 목록을 쓴다. 서버 파일은 없다
- 확인 질문(되묻기), 개선안 여러 개, 자동 다듬기, 에이전트 실행 중 다듬기, 질문 외 텍스트 다듬기는 범위 밖이다(PRD 7절)
- 사용량 기록의 용도 값 추가는 저장 구조 변경이며, 새 버전이 요청을 받기 전에 적용된다
