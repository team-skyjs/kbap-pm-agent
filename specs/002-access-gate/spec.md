# Feature Specification: 접근 제한

**Feature Branch**: `feat/access-gate`

**Created**: 2026-10-15

**Status**: Draft

**Input**: User description: "docs/prd/PRD-access-gate.md — 프론트와 API를 한 호스트명 아래로 모으고 Cloudflare Access로 허용된 사람만 들어오게 한다. 지금은 화면 주소와 API가 공개되어 누구나 화면을 열고 LLM 예산을 쓸 수 있다."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 허용된 팀원이 로그인 한 번으로 사용한다 (Priority: P1)

허용 목록에 있는 개발자가 서비스 주소를 연다. 이메일을 넣고 일회용 PIN으로 로그인하면 화면이 열리고, 그 자리에서 질문·제안·설정까지 모두 쓴다. 다음 날 다시 열어도 세션이 남아 있으면 로그인 없이 바로 들어간다.

**Why this priority**: 보호를 걸어도 팀이 불편해서 안 쓰면 실패다. 접근 제한의 사용자 가치는 "막힘 없이 쓰는 경험"에 있다.

**Independent Test**: 허용 이메일로 로그인 후 질문 하나를 보내 제안을 받고, 설정 화면을 열어 저장소·택사노미·Amplitude 상태를 확인한다. 모든 요청이 같은 호스트명으로 나간다.

**Acceptance Scenarios**:

1. **Given** 허용 목록의 이메일, **When** 서비스 주소를 열고 PIN으로 로그인, **Then** 채팅 화면이 뜨고 헬스 표시가 정상이다
2. **Given** 로그인된 상태, **When** 질문을 보냄, **Then** 진행 표시와 제안이 기존과 같은 형태로 돌아온다 (스트리밍 유지)
3. **Given** 로그인된 상태, **When** 설정 화면에서 Amplitude 연결을 시작해 승인 후 돌아옴, **Then** 연결 상태가 "연결됨"이 된다
4. **Given** 세션 유효 기간 안, **When** 브라우저를 닫았다 다시 염, **Then** 재로그인 없이 화면이 열린다

---

### User Story 2 - 허용되지 않은 요청은 서버에 닿지 않는다 (Priority: P1)

허용 목록에 없는 사람이 화면 주소나 API 주소를 안다. 열면 로그인 화면만 보이고, API를 직접 호출해도 로그인 응답만 돌아온다. 백엔드에는 요청이 도달하지 않는다.

**Why this priority**: 이 기능의 존재 이유다. LLM 예산과 대화 기록을 지킨다.

**Independent Test**: 허용되지 않은 상태에서 화면 주소, API 헬스 경로, 메시지 전송 경로를 각각 호출해 모두 로그인 응답(또는 거부)이고 백엔드 로그에 해당 요청이 없는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 로그인하지 않은 브라우저, **When** 서비스 주소를 염, **Then** 로그인 화면이 보이고 앱 화면은 보이지 않는다
2. **Given** 로그인 쿠키 없는 HTTP 클라이언트, **When** API 경로(헬스, 대화 목록, 메시지 전송)를 호출, **Then** 백엔드 응답이 아닌 접근 거부 응답이 오고 백엔드 요청 로그에 남지 않는다
3. **Given** 허용 목록에 없는 이메일, **When** PIN 로그인을 시도, **Then** 거부된다

---

### User Story 3 - 옛 공개 경로가 닫힌다 (Priority: P2)

이전에 쓰던 GitHub Pages 주소와 API 직접 호출 경로가 더 이상 열리지 않는다. 우회로가 없다.

**Why this priority**: 새 입구를 잠가도 옛 문이 열려 있으면 의미가 없다. 다만 새 입구가 동작한 뒤에 닫아야 하므로 P2다.

**Independent Test**: 옛 Pages 주소를 열면 404이고, 백엔드가 옛 Pages 출처의 요청을 허용 목록에서 뺐는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 접근 제한 적용 완료, **When** 옛 Pages 주소를 염, **Then** 404 또는 접속 불가다
2. **Given** 접근 제한 적용 완료, **When** 옛 Pages 출처로 API 사전 요청(preflight)을 보냄, **Then** 허용되지 않는다

---

### User Story 4 - 배포 한 번에 프론트와 백엔드가 함께 나간다 (Priority: P2)

main에 병합되면 프론트 정적 컨테이너와 백엔드 컨테이너가 같은 배포 흐름으로 홈서버에 올라간다. 운영 검사는 접근 제한을 통과하는 방식으로 돌아간다.

**Why this priority**: 프론트 배포처가 바뀌므로 자동 배포가 함께 바뀌어야 운영이 멈추지 않는다.

**Independent Test**: main 병합 후 배포 작업 하나가 두 이미지를 빌드·배포하고 헬스체크를 통과한다. 운영 검사를 돌려 통과한다.

**Acceptance Scenarios**:

1. **Given** main에 프론트 변경 병합, **When** 배포 작업 실행, **Then** 프론트 이미지가 새로 빌드되어 홈서버에서 교체된다
2. **Given** 접근 제한이 켜진 운영, **When** 운영 검사를 실행, **Then** 검사가 접근 제한을 통과해(서비스 토큰 또는 서버 내부 실행) 헬스와 같은 출처 호출을 확인한다

---

### Edge Cases

- 세션이 만료된 채 질문을 보내면: 스트리밍 요청이 로그인 응답을 받는다. 화면은 "다시 로그인" 안내를 보이고 입력값을 잃지 않는다
- 로그인 응답(HTML)을 API 응답으로 파싱하려 하면: 프론트가 계약 에러 형식이 아닌 응답을 "세션 만료"로 구분한다
- 긴 스트리밍(최대 170초) 중 접근 제한 계층이 연결을 끊는지: 확인 항목. 끊기면 부분 결과와 재시도 안내
- Amplitude 승인 후 콜백으로 돌아올 때 세션이 없으면: 로그인 후 콜백이 이어져야 한다. 안 되면 설정 화면에서 다시 연결 안내
- 허용 목록 변경: 대시보드에서 즉시 반영. 코드·재배포 없음

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 프론트 화면과 API는 같은 호스트명으로 제공되어야 한다. 프론트의 API 호출은 같은 출처의 상대 경로여야 한다
- **FR-002**: 허용 목록(이메일)에 있는 사람만 화면과 API에 접근할 수 있어야 한다. 로그인은 이메일 일회용 PIN으로 한다
- **FR-003**: 허용되지 않은 요청은 백엔드에 도달하지 않아야 한다. 경로 전체(헬스 포함)에 적용된다
- **FR-004**: 로그인 세션은 정해진 기간 동안 유지되어 재방문 시 재로그인이 필요 없어야 한다
- **FR-005**: 기존 기능(채팅 스트리밍, 제안 채택, 설정, Amplitude 승인 콜백)이 접근 제한 뒤에서 그대로 동작해야 한다
- **FR-006**: 프론트가 세션 만료 응답을 구분해 사용자에게 다시 로그인하도록 안내해야 한다
- **FR-007**: 옛 공개 프론트 주소는 닫히고, 백엔드의 허용 출처 목록에서 옛 주소가 제거되어야 한다
- **FR-008**: 배포 작업 하나가 프론트와 백엔드를 함께 빌드·배포해야 한다
- **FR-009**: 운영 검사가 접근 제한을 통과하는 방법을 갖추어야 한다
- **FR-010**: 허용 목록 변경에 코드 변경이나 재배포가 필요하지 않아야 한다

### Key Entities

- **허용 목록**: 접근이 허용된 이메일 집합. 대시보드에서 관리. 코드 밖
- **세션**: 로그인 후 브라우저에 남는 증표. 유효 기간 동안 재로그인 없음
- **프론트 컨테이너**: 정적 파일을 제공하는 서비스. 백엔드와 같은 네트워크·같은 호스트명

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 적용 후 1주 동안 허용 목록 밖에서 백엔드에 도달한 요청 0건 (접근 계층 로그와 백엔드 로그 대조)
- **SC-002**: 허용된 두 사람이 로그인 한 번으로 질문→제안 확인까지 추가 조작 없이 완료 (수동 확인)
- **SC-003**: 옛 Pages 주소와 옛 출처 API 호출이 모두 닫힘
- **SC-004**: 접근 제한 적용 전후 첫 진행 표시·완성 제안 시간이 기존 기준(5초·3분) 안에 유지

## Assumptions

- 사용자 2명. 역할·권한 구분 없음. 허용 목록 하나
- 접근 제한은 Cloudflare Access(Zero Trust 무료 플랜)로 하며, 홈서버 터널은 대시보드 관리형이라 경로 규칙과 정책은 사람이 대시보드에서 만든다
- 같은 호스트명에서 경로 기반으로 프론트·백엔드를 나눈다. 분기 위치는 plan.md가 정하며 웹 컨테이너 nginx다(ADR-22, research R6). 터널 경로 규칙도 가능하다(같은 홈서버의 다른 서비스가 사용 중)
- 스트리밍 응답(최대 170초)이 접근 계층을 통과한다. 검증 항목
- 허용 이메일 두 개는 사용자만 안다. 코드에 넣지 않는다
- 공유 토큰 장치(ACCESS_TOKEN)는 전환 기간(US2 운영 검증 전) 운영 필수로 켜 두고, 검증 후 배포의 필수 검사를 빼고 비운다(Phase 8). 코드 제거는 별도 결정
- 옛 Pages 폐쇄는 새 입구 검증 후 수행한다
