**Feature Branch**: `main` (단일 기능 그린필드 프로토타입. 기능 디렉토리 `specs/001-pm-agent-prototype/`)

**Status**: Draft

**Input**: User description: "docs/prd/PRD-kbap-pm-agent.md — 개발자 2명 팀에서 기획자 역할을 대신하는 채팅형 에이전트. 이벤트 택사노미(정의), FE 코드(맥락), Amplitude(지표)를 종합해 다음에 무엇을 만들지·어떻게 측정할지를 근거와 실행안까지 붙여 제안한다."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 근거 있는 기획 제안 받기 (Priority: P1)

기획 결정을 내려야 하는 개발자가 채팅에 결정 과제를 입력한다("가장 큰 이탈 지점을 찾아 개선안을 제안해줘"). 에이전트는 지표에서 이상 지점이나 기회를 찾고, 택사노미로 이벤트 의미를 확인하고, 코드로 실제 화면·동작 맥락을 확인한 뒤, **근거 → 제안 → 실행 단계 → 측정 방법** 네 부분으로 된 제안을 낸다. 개발자는 제안마다 채택 또는 보류를 표시한다.

**Why this priority**: PRD의 핵심 가정("세 소스를 종합한 제안이 채택할 만한 수준이 되는가")을 검증하는 유일한 경로다. 이것이 안 되면 나머지는 의미가 없다.

**Independent Test**: 택사노미와 저장소가 연결된 상태에서 결정 과제 하나를 입력하고, 네 부분이 모두 채워진 제안이 돌아오며 채택 표시가 저장되는지로 완전히 검증 가능.

**Acceptance Scenarios**:

1. **Given** 택사노미·저장소·지표 연결이 완료된 상태, **When** 개발자가 결정 과제를 입력, **Then** 응답에 근거(수치 또는 코드 위치 인용), 제안, 실행 단계, 측정 방법이 모두 포함된 제안이 하나 이상 표시된다
2. **Given** 제안이 표시된 상태, **When** 개발자가 "채택"을 누름, **Then** 제안 상태가 채택으로 바뀌고 결정 시각이 기록되며 대화를 다시 열어도 유지된다
3. **Given** 에이전트가 응답을 만드는 중, **When** 외부 조회가 진행됨, **Then** 개발자는 어떤 소스를 조회하고 있는지 중간 진행을 볼 수 있다(빈 화면에서 기다리지 않는다)
4. **Given** 외부 지표 서비스가 응답하지 않음, **When** 개발자가 질문, **Then** 에이전트는 가능한 소스(택사노미·코드)만으로 답하고 어느 근거가 빠졌는지 명시한다

---

### User Story 2 - 측정 설계 제안 받기 (Priority: P2)

새 기능의 효과를 측정해야 하는 개발자가 가설을 입력한다("장바구니 개선 효과를 측정하고 싶다"). 에이전트는 택사노미에서 이미 있는 이벤트를 찾고, 코드에서 해당 화면의 컴포넌트와 핸들러를 찾아, 퍼널 단계별로 기존 이벤트인지 새 이벤트인지 표시하고, 새 이벤트는 **어느 파일의 어느 함수에** 넣을지까지 적은 설계안을 낸다.

**Why this priority**: PRD 핵심 결과 2(설계 제안의 80%가 코드 위치까지 구체적)를 직접 검증한다. P1과 같은 엔진을 쓰되 출력 구조(퍼널·위치)가 추가된다.

**Independent Test**: 가설 하나를 입력하고, 반환된 퍼널의 각 단계에 기존/신규 표시가 있으며 신규 단계마다 파일·함수 위치가 채워져 있는지로 검증 가능.

**Acceptance Scenarios**:

1. **Given** 택사노미와 저장소가 연결된 상태, **When** 개발자가 측정 가설을 입력, **Then** 응답의 측정 방법에 2단계 이상의 퍼널이 있고 각 단계에 기존/신규 표시가 있다
2. **Given** 퍼널에 신규 단계가 포함됨, **When** 설계안이 표시됨, **Then** 신규 단계마다 이벤트 이름·파일·함수가 비어 있지 않다
3. **Given** 택사노미에 있는 이벤트가 코드에 없음, **When** 개발자가 그 이벤트가 포함된 가설을 입력, **Then** 에이전트는 "정의는 있으나 코드에서 발견되지 않음"을 근거에 명시한다

---

### User Story 3 - 대화 기록 보존과 재열기 (Priority: P3)

개발자가 과거 대화 목록을 보고 하나를 열어 당시의 제안과 채택 여부를 다시 본다.

**Why this priority**: 결정의 근거가 남아야 PRD 핵심 결과 1(채택 건수)을 측정할 수 있다. P1·P2 없이도 저장·조회만으로 독립 검증 가능.

**Independent Test**: 대화를 두 개 만들고 목록에서 둘이 보이는지, 하나를 열어 메시지와 제안 상태가 그대로인지로 검증 가능.

**Acceptance Scenarios**:

1. **Given** 대화가 2개 이상 존재, **When** 개발자가 목록을 열람, **Then** 최근 순으로 제목·시각·제안 수가 보인다
2. **Given** 채택 표시된 제안이 있는 대화, **When** 다시 열기, **Then** 메시지 순서와 제안의 채택 상태가 보존되어 있다

---

### User Story 4 - 소스 연결 설정 (Priority: P4)

개발자가 택사노미 파일을 올리고, 프론트 저장소 주소를 등록하고, 지표 서비스 연결을 승인한다. 각 연결의 상태(연결됨·미연결·마지막 동기화)를 한 화면에서 본다.

**Why this priority**: P1·P2의 전제 조건이지만 사용자 가치 자체는 없다. 연결이 없을 때도 가짜 데이터로 P1~P3를 시연할 수 있어야 하므로 우선순위를 뒤로 둔다.

**Independent Test**: 택사노미 업로드 후 이벤트 수가 표시되고, 저장소 등록 후 동기화 시각이 갱신되며, 지표 연결 승인 후 상태가 연결됨으로 바뀌는지로 검증 가능.

**Acceptance Scenarios**:

1. **Given** 택사노미 파일이 정의된 형식, **When** 업로드, **Then** 읽힌 이벤트 개수와 갱신 시각이 표시된다
2. **Given** 유효한 저장소 주소, **When** 등록 후 동기화, **Then** 분석 대상 파일 수와 동기화 시각이 표시된다
3. **Given** 지표 서비스 미연결, **When** 연결 시작, **Then** 승인 화면으로 이동하고 승인 후 돌아오면 상태가 연결됨으로 바뀐다
4. **Given** 잘못된 형식의 택사노미, **When** 업로드, **Then** 어느 항목이 왜 잘못됐는지 알려주고 기존 택사노미는 유지된다

---

### Edge Cases

- 에이전트 응답이 매우 오래 걸릴 때(복수 소스 조회): 중간 진행을 보여주고, 상한 시간을 넘으면 그때까지의 근거로 부분 답변과 사유를 돌려준다
- 외부 서비스(지표·저장소·모델) 중 하나가 실패할 때: 나머지 소스로 답하고 빠진 근거를 명시한다. 서비스 전체가 죽지 않는다
- 비공개 저장소: 서버에 보관된 접근 토큰으로 읽는다. 토큰이 없거나 만료되면 연결 상태에 사유를 표시한다
- 택사노미에 없는 이벤트가 코드에 있을 때: 근거에 "코드에만 존재, 정의 없음"으로 표시한다
- 모델 호출 예산이 상한에 닿았을 때: 모델 호출을 거절하고 사유를 돌려준다. 저장된 대화 조회는 계속 된다
- 같은 질문을 반복할 때: 코드 분석 결과를 재사용해 비용과 시간을 줄인다
- 저장소 커밋이 바뀐 뒤: 바뀐 파일만 다시 분석한다

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 자연어 질문을 받아 에이전트 응답을 돌려줘야 하며, 응답 생성 중 어떤 소스를 조회하는지 중간 진행을 사용자에게 보여야 한다
- **FR-002**: 에이전트 제안은 근거·제안·실행 단계·측정 방법 네 부분으로 구조화되어야 하며, 본문 문자열 안에 섞여 있으면 안 된다
- **FR-003**: 근거는 출처 유형(지표 수치, 택사노미 정의, 코드 위치)을 구분해 표시해야 한다. 코드 위치는 파일·함수를 포함한다
- **FR-004**: 측정 방법의 퍼널은 단계마다 이벤트 이름과 기존/신규 구분을 포함해야 하며, 신규 이벤트는 파일·함수 위치가 필수다
- **FR-005**: 사용자는 제안마다 채택·보류를 표시할 수 있어야 하고, 상태와 결정 시각이 보존되어야 한다
- **FR-006**: 시스템은 대화·메시지·소스 조회 기록·제안·채택 여부를 영구 저장하고, 대화 목록과 상세를 조회할 수 있어야 한다
- **FR-007**: 사용자는 정의된 형식의 택사노미 파일을 올릴 수 있어야 하며, 시스템은 이벤트별 정의와 속성을 읽어 에이전트의 판단 근거로 써야 한다
- **FR-008**: 사용자는 프론트 저장소 주소를 등록하고 동기화할 수 있어야 하며, 시스템은 그 코드에서 이벤트 호출 지점과 화면 맥락을 찾을 수 있어야 한다
- **FR-009**: 시스템은 지표 서비스에 사용자 승인 흐름으로 연결하고, 연결 상태를 표시해야 한다
- **FR-010**: 외부 서비스 중 하나가 실패해도 시스템은 나머지 소스로 응답하고 빠진 근거를 명시해야 한다
- **FR-011**: 시스템은 외부 연결 없이도 미리 정한 예시 응답으로 전체 사용자 흐름을 시연할 수 있는 실행 모드를 제공해야 한다
- **FR-012**: 시스템은 모델 호출 비용에 상한을 두고, 상한 도달 시 호출을 거절하며 사유를 알려야 한다. 모든 모델 호출의 사용량을 기록해야 한다
- **FR-013**: 시스템은 코드 분석 결과를 재사용하고, 저장소가 바뀌면 바뀐 부분만 다시 분석해야 한다
- **FR-014**: 추론에 쓰는 모델은 코드 변경 없이 설정으로 바꿀 수 있어야 한다

### Key Entities

- **대화(Conversation)**: 하나의 기획 과제를 다루는 메시지 묶음. 제목, 생성·갱신 시각, 제안 수
- **메시지(Message)**: 사용자 질문 또는 에이전트 응답. 순서, 역할, 본문, 포함된 제안, 모델 사용량·비용(에이전트 응답만)
- **소스 조회(ToolCall)**: 에이전트가 응답을 만들며 수행한 조회 하나. 소스 종류(지표·택사노미·코드), 입력, 결과 요약, 소요 시간. 비용은 조회 단위가 아니라 메시지 단위로 집계한다
- **제안(Proposal)**: 근거 목록, 제안 본문, 실행 단계 목록, 측정 방법(퍼널 단계 목록), 상태(대기·채택·보류), 결정 시각
- **퍼널 단계(FunnelStep)**: 순서, 이벤트 이름, 기존/신규, 조건, 신규인 경우 파일·함수 위치와 속성
- **택사노미(Taxonomy)**: 이벤트 정의 집합. 이벤트 이름, 설명, 속성 목록, 갱신 시각
- **연결 설정(Settings)**: 저장소 주소와 마지막 동기화, 택사노미 상태, 지표 서비스 연결 상태, 사용 중인 모델

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 프로토타입 출시 후 4주 동안 개발자가 채택 표시한 제안이 4건 이상이다 (PRD 핵심 결과 1)
- **SC-002**: 측정 설계 제안 중 80% 이상이 신규 이벤트의 파일·함수 위치를 포함해 추가 조사 없이 구현 가능하다 (PRD 핵심 결과 2, 수동 채점)
- **SC-003**: 제안이 인용한 지표 수치를 지표 서비스에서 직접 확인했을 때 90% 이상 일치한다 (PRD 핵심 결과 3)
- **SC-004**: 결정 과제 입력 후 첫 중간 진행 표시까지 5초 이내, 완성된 제안까지 3분 이내다
- **SC-005**: 외부 연결 없이 시연 모드로 사용자 스토리 1~3을 처음부터 끝까지 수행할 수 있다
- **SC-006**: 4주 운영 동안 모델 호출 비용 합계가 200달러를 넘지 않는다

## Assumptions

- 사용자는 개발자 2명이다. 인증·권한·멀티테넌시는 범위 밖이다 (PRD 8절)
- 세 소스를 종합한 제안이 "채택할 만한" 수준이 된다. 이것이 가장 큰 가정이며 SC-001로 검증한다 (PRD 7.4)
- 택사노미는 정의된 단일 형식으로 전달된다 (ADR-12). 다른 형식 변환은 범위 밖이다
- 프론트 코드의 이벤트 호출은 검색으로 찾을 수 있는 일관된 패턴을 쓴다 (PRD 7.4). 아니면 코드 분석 비용이 크게 늘어난다
- 지표 서비스는 공식 원격 연결 방식(승인 기반)을 제공하며 조회 전용이다. 이벤트 전송은 하지 않는다
- 비공개 저장소 접근은 서버에 보관된 토큰으로 한다 (ADR-13)
- v1은 질문에 반응하는 모드만 제공한다. 먼저 제안하는 능동 모드, 일일 리포트, 디자인 시안 생성, 이슈 등록은 다음 버전이다 (ADR-14, PRD 8절)
- 백엔드 코드 분석, 코드 자동 수정·PR 생성은 범위 밖이다 (PRD 8절)
