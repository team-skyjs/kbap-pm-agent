# Feature Specification: Amplitude 서버 고정 인증

**Feature Branch**: `feat/amplitude-rest`

**Created**: 2026-10-17

**Status**: Draft

**Input**: User description: "docs/prd/PRD-amplitude-server-auth.md — Amplitude 연동을 사람이 하루마다 다시 승인하지 않아도 되게 서버 고정 키로 바꾼다. 조회가 안 되는 상태면 모델을 돌리기 전에 멈춘다. 실행별 Amplitude 상태를 기록한다."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 지표가 붙은 답을 재승인 없이 받는다 (Priority: P1)

개발자가 지표가 필요한 질문을 보낸다. 서버는 고정 키로 Amplitude를 조회하고, 에이전트는 세그멘테이션·퍼널·리텐션 수치와 이벤트 맥락을 근거로 답한다. 하루가 지나도, 서버를 재시작해도 다시 연결할 일이 없다.

**Why this priority**: PRD의 첫 목표(재승인 0)이자 제품 가치(수치 있는 제안)의 전제다.

**Independent Test**: 서버에 키를 넣고 지표 질문을 보내 Amplitude 도구 호출이 성공하고 답에 수치 근거가 있는지 본다. 24시간 뒤와 재시작 뒤에 같은 질문을 다시 해서 같은 결과인지 본다.

**Acceptance Scenarios**:

1. **Given** 서버에 Amplitude 키 설정, **When** 퍼널 질문, **Then** 에이전트가 Amplitude 퍼널을 조회하고 답의 근거에 수치가 있다
2. **Given** 같은 설정, **When** 하루 뒤·재시작 뒤 질문, **Then** 사람의 조작 없이 같은 조회가 된다
3. **Given** 이벤트 이름이 필요한 질문, **When** 에이전트가 맥락을 조회, **Then** Amplitude 이벤트·속성 목록과 업로드한 택사노미 설명이 함께 쓰인다
4. **Given** 90일을 넘는 기간이나 잘못된 조합의 조회 요청, **When** 도구가 받는다, **Then** 조회하지 않고 이유를 모델에게 돌려줘 모델이 고쳐 다시 묻는다
5. **Given** 어떤 조회든, **When** 도구가 Amplitude를 부른다, **Then** 읽기 전용 조회만 한다(차트·택사노미를 만들거나 바꾸지 않는다)

---

### User Story 2 - 조회가 안 되면 실행 전에 안다 (Priority: P1)

키가 없거나, 인증이 실패하거나, 요청 한도를 넘었으면 메시지를 보내는 순간 "Amplitude 조회 불가: 이유" 안내가 뜨고 모델은 돌지 않는다. 사용자는 "Amplitude 없이 진행"을 골라 다시 보낼 수 있고, 그러면 답에 Amplitude를 쓰지 않았다는 사실이 적힌다.

**Why this priority**: PRD의 둘째 목표(비용을 쓰기 전에 멈춤)다.

**Independent Test**: 키를 비운 서버, 틀린 키 서버, 한도 초과를 흉내 낸 서버에서 각각 질문해 거절 안내의 이유가 다르고 사용량 기록이 생기지 않는지 본다. "없이 진행"으로 다시 보내 답이 오는지 본다.

**Acceptance Scenarios**:

1. **Given** 키 없음, **When** 질문, **Then** 실행 전에 "키가 설정되어 있지 않습니다" 안내로 거절되고 모델 호출·사용자 메시지 저장이 없다
2. **Given** 틀린 키(인증 실패), **When** 질문, **Then** "인증에 실패했습니다" 안내로 거절된다
3. **Given** 요청 한도 초과, **When** 질문, **Then** "요청 한도를 넘었습니다(잠시 후 다시)" 안내로 거절된다
4. **Given** 거절 안내, **When** "Amplitude 없이 진행", **Then** 같은 질문이 실행되고 답에 Amplitude를 쓰지 않았다는 사실이 있다
5. **Given** 거절 안내, **When** 사용자가 아무것도 하지 않음, **Then** 입력값은 입력창에 남아 있다

---

### User Story 3 - 설정 화면은 서버 키 상태만 보여 준다 (Priority: P2)

운영자가 설정 화면을 열면 Amplitude 영역에 "서버 키로 연결됨" 또는 "키 없음"만 보인다. "연결"·"다시 연결" 버튼과 승인 창은 없다.

**Why this priority**: 재승인 작업을 없앤 결과를 화면에 맞춘다.

**Independent Test**: 키가 있는 서버와 없는 서버에서 설정 화면을 열어 두 상태가 라벨로 구분되고 버튼이 없는지 본다.

**Acceptance Scenarios**:

1. **Given** 키 설정, **When** 설정 화면, **Then** "서버 키로 연결됨"이 보이고 키 값은 어디에도 보이지 않는다
2. **Given** 키 없음, **When** 설정 화면, **Then** "키 없음"과 서버 환경 변수를 설정하라는 짧은 안내가 보인다
3. **Given** 설정 화면, **When** Amplitude 영역을 본다, **Then** 연결·다시 연결 버튼이 없다

---

### User Story 4 - 실행별 Amplitude 상태가 남는다 (Priority: P2)

팀이 언제든 조회 한 줄로 "Amplitude를 쓴 실행 / 사용자가 건너뛴 실행 / 실행 중 인증이 끊긴 실행"의 수를 본다. 전환 뒤 "인증 끊김으로 완료된 실행"은 0이어야 한다.

**Why this priority**: PRD 핵심 결과 2의 측정이다.

**Independent Test**: 정상 실행 1회, 건너뛰기 실행 1회를 한 뒤 상태별 건수 조회가 각각 1인지 본다.

**Acceptance Scenarios**:

1. **Given** 사전 점검 통과 실행, **When** 완료, **Then** 상태 "사용"이 남는다
2. **Given** "Amplitude 없이 진행" 실행, **When** 완료, **Then** 상태 "건너뜀"이 남는다
3. **Given** 실행 중 Amplitude 도구가 인증 실패를 받음, **When** 완료, **Then** 상태 "불가"가 남는다

---

### Edge Cases

- 시연 모드: 사전 점검을 하지 않고 통과한다. 상태 기록은 남기지 않는다(집계 제외)
- 사전 점검은 통과했지만 실행 중 한도에 걸림: 그 도구 호출만 실패로 남고 실행은 나머지로 계속된다(기존 실패 처리)
- 키가 한쪽만 있음(API 키만, 시크릿 키만): "키 없음"과 같다
- 이전에 저장된 OAuth 토큰: 전환 시 지운다(쓰기 권한이 섞여 발급된 토큰이었다)
- 커스텀 이벤트: `ce:` 접두어 이름을 그대로 조회에 쓴다(현재 프로젝트에는 없음)
- 세그멘테이션에 "신규 사용자"를 요구: 세그멘테이션은 `any`·`active`만 받으므로 도구가 이유와 함께 거절하고, 신규 사용자는 퍼널에서만 받는다
- 결과가 매우 큼(긴 기간·많은 그룹): 행 수와 전체 길이 상한으로 줄이고 줄였다는 표시를 남긴다

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 서버는 환경 변수의 프로젝트 API 키와 시크릿 키로 Amplitude 조회 API를 부른다. 키 값은 응답·로그·기록 어디에도 내보내지 않는다
- **FR-002**: 에이전트는 Amplitude 도구 두 개를 쓴다. 지표 조회는 세그멘테이션·퍼널·리텐션을 한 도구의 종류 인자로 받고 조회 조건은 구조화된 인자다. 이벤트 맥락은 이벤트·속성 목록에 업로드한 택사노미 설명을 합친다
- **FR-003**: 도구는 조회 전용 엔드포인트만 부른다. 그 밖의 경로나 쓰기 메서드는 코드에서 막는다
- **FR-004**: 지표 조회는 기간 90일 상한, 종류별 이벤트 개수·인자 조합 규칙, 세그멘테이션 사용자 유형(`any`·`active`)과 퍼널 사용자 유형(`new`·`active`)을 검사하고, 어기면 조회 없이 이유를 돌려준다. 커스텀 이벤트 접두어(`ce:`)는 그대로 통과시킨다
- **FR-005**: 결과는 모델이 읽기 좋은 압축표(시계열 표와 요약, 퍼널 단계표, 리텐션 코호트표)로 줄이고 기존 결과 크기 상한을 적용한다
- **FR-006**: 이벤트·속성 목록은 15분 동안 재사용한다
- **FR-007**: 메시지를 보낼 때 예산 검사 다음에 Amplitude 사전 점검을 하고, 키 없음·인증 실패·한도 초과·연결 실패를 구분한 안내로 실행 전에 거절한다. 거절 시 모델 호출과 메시지 저장이 없다
- **FR-008**: 사용자는 거절 뒤 "Amplitude 없이 진행"으로 다시 보낼 수 있고, 그 답에는 Amplitude를 쓰지 않았다는 사실이 적힌다
- **FR-009**: 설정 화면의 Amplitude 상태는 "서버 키로 연결됨"과 "키 없음" 둘뿐이며, 연결·다시 연결 동작과 승인 경로는 없다
- **FR-010**: 실행마다 Amplitude 상태(사용·불가·건너뜀)를 기록하고 조회 한 줄로 셀 수 있다
- **FR-011**: 이전 OAuth 연결 코드·저장된 토큰·승인 경로를 제거한다. 두 경로를 함께 두지 않는다
- **FR-012**: 시연 모드는 외부 Amplitude를 부르지 않는다
- **FR-013**: 새 의존성을 추가하지 않는다

### Key Entities

- **Amplitude 키 설정**: API 키, 시크릿 키, 조회 주소. 서버 환경 변수에만 있다
- **실행의 Amplitude 상태**: 사용·불가·건너뜀. 에이전트 답 메시지 하나에 하나
- **이벤트 맥락**: 이벤트 이름·범주·설명(업로드 택사노미 우선)·출처, 이벤트별 속성 목록

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 전환 뒤 재승인 횟수 0(설정 화면에 연결 동작이 없다)
- **SC-002**: 전환 뒤 "실행 중 인증 끊김(불가)"으로 완료된 실행 수 0(상태 조회 한 줄)
- **SC-003**: 키 없음·인증 실패·한도 초과 세 경우 모두 모델 호출 0회로 거절된다(사용량 기록으로 확인)
- **SC-004**: 운영에서 쓰던 질문 유형(세그멘테이션·퍼널·리텐션·이벤트 맥락)을 새 도구로 다시 물었을 때 같은 종류의 수치 근거가 나온다(실제 키 수동 확인)
- **SC-005**: 기존 기능 회귀가 없다

## Assumptions

- K-Bap 프로젝트 플랜은 Dashboard REST API와 Taxonomy API를 허용한다(형제 레포가 같은 프로젝트에서 운영 중, PRD 6.4)
- 운영 3일간 Amplitude 호출이 모두 세그멘테이션·퍼널·리텐션·이벤트 맥락 범위였으므로, 두 도구로 덮인다(PRD 6.4 가정, 실제 키로 확인)
- Amplitude "MCP 서비스 계정"의 존재 여부는 열린 질문으로 남기고 이번 전환을 막지 않는다(사용자 지시: 중간 확인 없이 진행)
- 사전 점검 실패 시 "그래도 진행"을 두되 기본은 거절이다(PRD 6.4 첫 버전 기본값)
- 같은 키를 쓸지 새 키를 발급할지는 운영자가 정한다
