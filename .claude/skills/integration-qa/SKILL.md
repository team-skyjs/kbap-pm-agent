# Integration QA — 경계면 교차 검증

따로 잘 되는 두 코드가 붙으면 깨진다. 이유는 거의 항상 같다. 한쪽이 계약서를 조금 다르게 읽었다. 그래서 검증은 **세 개를 동시에 읽는 것**이다. 계약서, 생산자 코드, 소비자 코드.

## 0. 시작

1. `_workspace/01_cto_api-contract.md`를 읽는다. 이것이 기준이다
2. `_workspace/03_qa_findings.md`가 있으면 읽는다. 열린 결함부터 재검증한다
3. 개발자의 `[모듈 완료]` 메시지에서 모듈·엔드포인트·실행 방법·연동 상태를 확인한다

## 1. 정적 대조 (양쪽 동시 읽기)

모듈의 엔드포인트마다 아래 표를 머릿속에 채운다. 하나라도 비면 통과시키지 않는다.

| 항목 | 계약서 | 백엔드 (생산자) | 프론트 (소비자) |
|------|--------|---------------|---------------|
| 경로·메서드 | §x.y | 라우터 정의 파일:라인 | 호출 코드 파일:라인 |
| 요청 shape | JSON 예시 | 파싱/검증 코드 | 요청 생성 코드 |
| 응답 shape (감싸기 포함) | JSON 예시 | 응답 생성 코드 | 타입 + 파서 |
| 필드 명명 (camel/snake) | 공통 규칙 | 실제 키 | 실제 키 |
| 에러 형식 | 공통 에러 JSON | 에러 응답 코드 | 에러 파싱·표시 코드 |
| 비동기/스트리밍 | 즉시 vs 최종 | 어떤 시점에 무엇을 보내나 | 어떤 시점의 무엇을 읽나 |

이 프로젝트에서 특히 볼 곳:
- **제안 구조:** 근거·제안·실행단계·측정방법 네 필드가 백엔드에서 구조화되어 나오고, 프론트가 그 필드로 카드를 그리는가. 본문 문자열을 정규식으로 쪼개고 있으면 결함
- **채택/보류:** 프론트가 보내는 값과 백엔드가 저장하는 enum이 같은가. DB 컬럼까지 추적
- **스트리밍:** SSE/WS를 쓰면 이벤트 이름과 종료 신호가 양쪽에서 같은가
- **mock 잔존:** 연동 상태가 "실제"라고 보고된 모듈에 가짜 응답 코드가 남아 있지 않은가
- **GitHub Pages 경로:** 프론트 라우팅·에셋 경로가 `/{repo}/` 접두사에서 깨지지 않는가. 백엔드 주소가 하드코딩되어 있지 않은가

타입 캐스팅(`as`, `any`, 제네릭 `<T>` 단독)은 컴파일러를 통과시킬 뿐이다. 발견하면 런타임 검증(2절)으로 반드시 확인한다.

## 2. 실행 검증

1. 개발자가 알려준 명령으로 백엔드를 띄운다. 안 뜨면 그것이 첫 결함이다
2. 계약서의 요청 예시를 그대로 `curl`로 보낸다. 응답을 계약서 응답 예시와 **키 단위로** 비교한다
3. 프론트를 띄우고 해당 화면을 연다. 네트워크 요청이 2번과 같은 요청인지, 응답을 받아 화면에 그리는지 확인한다
4. 에러 경로 하나는 반드시 친다. 잘못된 요청을 보내 공통 에러 형식으로 오고 프론트가 그것을 표시하는지
5. 양쪽 개발자가 남긴 검사 스크립트를 실행한다. 실패하면 결함

외부 키(Amplitude, LLM)가 없으면 가짜 연동 경로만 검증하고 리포트에 **미검증**으로 쓴다. 통과로 적지 않는다.

## 3. 결함 형식 (`_workspace/03_qa_findings.md`에 누적 + 담당자에 SendMessage)

```
### QA-{번호}: {한 줄}
- 모듈: {backend|frontend} / {모듈}
- 경계면: {엔드포인트} {요청|응답|에러|스트림}
- 기대: {계약서 §x.y 인용, 실제 JSON 조각}
- 실제: {파일:라인, 실제 JSON 조각 또는 코드}
- 수정 방향: {어느 쪽을, 어떻게}
- 수신: {backend-dev | frontend-dev | 둘 다 | cto}
- 상태: 열림 | 수정됨 | 확인됨
```
경계면 결함은 **둘 다**에게 보낸다. 한쪽만 고치면 다른 쪽이 또 깨진다.
계약서가 모호해서 양쪽이 다르게 읽은 경우 수신은 `cto`다. 개발자 잘못이 아니다.

## 4. 재검증

개발자의 `[수정됨]` 메시지를 받으면 해당 결함만 1·2절로 다시 본다. 통과하면 상태를 "확인됨"으로. 같은 결함이 두 번 열리면 CTO에게 구조적 원인을 보고한다.

## 5. 최종 리포트 (`_workspace/03_qa_report.md`)

```
# QA 리포트 — {날짜}
## 요약: 통과 N / 실패 N / 미검증 N
## 모듈별 결과
| 모듈 | 경계면 | 결과 | 결함 ID | 비고 |
## 미검증 항목과 이유
## 남은 위험
## 실행 방법 (사용자가 직접 재현할 수 있게)
```
"남은 위험"에는 미검증 외부 연동, 타입 캐스팅으로 우회된 지점, 가정 상태 ADR에 의존하는 부분을 쓴다.
