# Tech Decision — 결정을 세 문서로 남기는 법

CTO의 산출물은 세 파일이다. 구현자는 이 세 파일만 읽고 시작할 수 있어야 한다. 그 외 설명은 전부 생략한다.

## 0. 시작 전

1. `docs/prd/PRD-kbap-pm-agent.md`를 읽는다. 특히 5절 제약, 7.3 기술, 8절 비목표
2. `_workspace/01_cto_*`가 있으면 읽는다. 있으면 **갱신 모드**: 바뀐 결정만 추가하고 이전 항목을 "대체됨"으로 표시한다. 전체를 다시 쓰지 않는다
3. 사용자가 밝힌 스택 선호를 확인한다. 없으면 CTO가 정하되 ADR에 "가정"으로 표시한다

## 1. `_workspace/01_cto_tech-decisions.md` — ADR 목록

결정할 것만 결정한다. 기준: **지금 안 정하면 FE·BE가 서로 다른 가정으로 코드를 쓰게 되는가?** 그렇지 않으면 구현자에게 위임한다고 적는다.

반드시 포함할 ADR (이 프로젝트에서 되돌리기 어려운 것):

| # | 결정 | 왜 지금인가 |
|---|------|-----------|
| 1 | 백엔드 언어·프레임워크 | 에이전트 루프, MCP 클라이언트 라이브러리 생태계가 언어에 묶임 |
| 2 | 에이전트 루프 구현 방식 (직접 vs SDK) | 코드 구조 전체를 결정 |
| 3 | 프론트 프레임워크·빌드 | GitHub Pages 정적 배포 + 프로젝트 페이지 경로 제약 |
| 4 | FE↔BE 연결 | 홈서버 공개 방식(터널/프록시), CORS, 스트리밍 여부(SSE/WebSocket/없음) |
| 5 | MySQL 스키마 뼈대 | 세션·메시지·도구호출·제안·채택 테이블과 관계 |
| 6 | 코드 분석 비용 통제 | grep 선필터 + 요약 캐시 + 갱신 시점. 200달러 예산 |
| 7 | 외부 연동 추상화 | Amplitude MCP, GitHub, LLM 각각 가짜 구현으로 교체 가능한 경계 |
| 8 | 로컬 실행·Docker 구성 | `docker compose up` 한 번으로 BE+MySQL |

명시적으로 위임할 것: UI 라이브러리, 캐시 저장 매체(파일/DB), 추론 모델 기본값, 로깅 방식.

ADR 형식 (항목당 10줄 이내):
```
### ADR-N: {결정 한 줄}
- 결정: {무엇}
- 이유: {왜}
- 버린 대안: {무엇을, 왜 안 했나}
- 바꾸면 영향: {이 결정을 뒤집을 때 다시 써야 하는 것}
- 상태: 확정 | 가정 | 대체됨(→ADR-M)
```

## 2. `_workspace/01_cto_api-contract.md` — API 계약서

이 문서가 FE·BE·QA의 **유일한** 경계 기준이다. 모호함 하나가 QA 결함 하나다.

문서 구조:
```
## 공통
- Base URL: 환경변수 이름
- 에러 응답 형식: 모든 엔드포인트 공통 JSON (예시 포함)
- 날짜·ID 형식, 필드 명명 규칙 (camelCase 고정 등)
- 스트리밍 방식 (쓴다면 이벤트 형식까지)

## 엔드포인트
### {METHOD} {path}
- 용도: 한 줄
- 요청: JSON 예시 (실제 값으로)
- 응답 200: JSON 예시 (실제 값으로, 감싸는 구조까지 정확히)
- 응답 에러: 발생 가능한 코드와 공통 형식 참조
- 비고: 비동기면 즉시 응답과 최종 결과를 분리해 명시
```

이 프로젝트에서 빠지면 안 되는 엔드포인트: 대화 목록, 대화 생성, 메시지 전송(에이전트 응답), 대화 상세, 제안 채택/보류, 설정 조회(연결된 저장소·모델). 제안은 **근거·제안·실행단계·측정방법** 네 필드가 구조화되어 있어야 프론트가 카드로 그릴 수 있다. 본문 문자열에 섞어 보내지 않는다.

예시 JSON은 `{...}`, `string`, `any` 같은 자리표시자 대신 실제 값으로 쓴다. 자리표시자는 양쪽이 다르게 채운다.

## 3. `_workspace/01_cto_task-split.md` — 작업 분할

FE와 BE 각각 모듈 단위로. 모듈 = QA가 따로 검증할 수 있는 단위.

```
## backend
| 순서 | 모듈 | 포함 엔드포인트 | 완료 기준 | 의존 |
## frontend
| 순서 | 모듈 | 호출 엔드포인트 | 완료 기준 | 의존 |
## 통합 지점
- {FE 모듈} ↔ {BE 모듈}: mock→실제 전환 시점
```

첫 모듈은 양쪽 모두 "서버 뜬다 / 화면 뜬다 + 헬스체크 왕복"으로 잡는다. QA가 가장 먼저 검증할 수 있는 최소 경계면이다.

## 4. 끝내기 전 확인

- 계약서의 모든 엔드포인트가 작업 분할의 어느 모듈에든 들어 있는가
- PRD 비목표(인증, 백엔드 코드 분석, 코드 자동 수정)를 하는 결정이 없는가
- 계약서 JSON 예시에 자리표시자가 남아 있지 않은가
- "가정" 상태 ADR을 사용자에게 보고할 목록으로 뽑아 두었는가
